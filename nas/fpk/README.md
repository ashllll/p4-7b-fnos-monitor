# NAS 屏幕伴侣

把飞牛 NAS 的运行状态（CPU / 内存 / 网络 / 存储 / 阵列 / 温度）以**只读**方式提供给局域网内的屏幕设备。管理界面在飞牛桌面里打开。

**不需要 SSH，不需要 NAS 管理员密码，不使用 root 运行，不需要任何文件授权目录。**

---

## 它做什么

- 在 NAS 上常驻一个只读采集服务，按你设定的间隔读一次系统状态。
- 开一个供开发板读取的独立端口（默认 **8798**），默认 **HTTPS**。
- 在飞牛桌面里提供一个管理页：概览、能力矩阵、设备配对、服务设置、诊断五个标签页。
- 设备要先用**配对码**换到一枚令牌才能读数据；令牌在 NAS 侧只存 SHA-256，明文只在配对成功那一刻出现一次。

## 它不做什么

- **不写任何系统状态。** 采集全是读 `/proc`、`/sys`、`/proc/mounts` 这些只读来源。
- **不碰你已有的服务。** 尤其是开发版采集器（8799 端口、systemd 单元、`/usr/local/bin` 下的文件）——不在本应用管理范围内，安装、升级、卸载都不会改动或删除它。
- **端口冲突时不越界。** 如果你设的端口已被别的进程占用，应用会干净报错并告诉你是哪个端口，**绝不结束那个进程**。
- **不承诺 SMART / 硬盘健康。** 首版不读这些（权限与兼容性都还没验完）。
- **容器信息默认关闭。** 要读容器状态得显式打开（需要 Docker Socket，属于额外权限）。

## 安装

应用中心 → 手动安装 → 选择 `nasscreencompanion.fpk`。

安装向导里会问四件事，都能随时在管理页改：

| 向导项 | 默认 | 说明 |
| --- | --- | --- |
| 开发板读取端口 | `8798` | **别填 8799**，那通常是开发版采集器占着的 |
| 监听地址 | 内网所有网卡 | 选「仅本机」时管理页仍可用，但开发板读不到 |
| 开发板读取鉴权 | 配对令牌 | 「内网免令牌」只建议排障时短暂使用 |
| 传输加密（HTTPS） | 开 | 首次启动自动生成自签证书；关掉是明文，仅排障 |
| 采集容器状态 | 关 | 打开后需要 Docker Socket |
| 采集间隔 | 1.0 秒 | |

依赖：`python312` 应用。没装的话应用中心会提示。

## 第一次打开

从飞牛桌面点开本应用 → 打开的是管理页。先看两个地方：

1. **「能力矩阵」**：逐项列出每个数据来源（`/proc/stat`、`/proc/meminfo`、`/proc/mdstat`、`/sys/class/hwmon`……）在**包用户身份下**能不能读到，以及运行身份（uid/用户名）。哪一项是红的，就说明那类数据在这台机器上采不到——这一页就是权限的实测结果，不是承诺。
2. **「诊断」**：服务自检 + 日志尾巴。端口占用、证书状态、Socket 绑定都会写在这里。

## 与开发板配对

三步：

1. **在 NAS 管理页「设备配对」点「生成配对码」**，得到 6 位数字。
2. **在开发板屏幕上输入这 6 位**，点键盘上的「确认」。
3. **核对指纹**：板子会把 NAS 证书的 SHA-256 指纹分 4 行显示，与管理页「传输加密」里显示的指纹**逐段比对**。一致才点「接受并配对」。

> **为什么要人工比对？** 板子只认这一张证书（证书固定），而"这一张"是不是你的 NAS，只能由你当面确认。指纹对不上就点「取消」——那说明中间可能有人在转发证书。
>
> 板子上的指纹是**自己**从证书算出来的，不是读服务器给的字段——否则同时伪造证书和那个字段就能骗过比对。

配对成功后，板子会把地址、令牌、证书写进自己的存储器，以后只走加密连接读数据。

**撤销设备**：管理页「设备配对」里对某台设备点「撤销」，板子下次读数据会被拒绝，需要重新配对。

## 换 IP / 换证书会怎样

- **NAS 换 IP**：板子按配对时记的地址连，连不上就会在总览页显示「连不上 NAS」，需要重新配对（或在板子上改地址）。
- **证书重新生成**（比如你手动删了证书，或证书到期后自动重签）：指纹会变，**所有已配对设备立即失效**，必须重新配对。管理页「诊断」里能看到当前指纹。
- **只关掉再打开 TLS**：**证书不会重新生成，指纹不变**，已配对设备不用重新确认。

## 常见问题

**装上以后开发板读不到。**
按顺序查：管理页「诊断」→ 端口是不是被占用（向导里设的端口和实际监听的是不是同一个）→ 监听地址是不是「仅本机」→ 开发板「配对」页显示的错误是哪一种（连不上 / 握手失败 / 令牌被拒，板子会分别给不同提示）。

**端口 8799 有东西在跑，要紧吗？**
那是开发版采集器，本应用不碰它。你可以继续用 8798。

**关掉 TLS 会怎样？**
遥测面变成明文 HTTP，任何人拿到令牌就能读。配对令牌仍然是必需的。**建议只在排障时短暂关闭**，诊断页会显示成 warn。

**卸载会留下什么？**
停止服务、释放端口、删除本应用的配置与配对令牌（**开发板需要重新配对**）。不影响你的其他服务、不影响开发版采集器、也不影响开发板上的固件与设置（只是会读不到状态）。

## 装不上、起不来的时候

这两件事最可能发生在你面前，而这时你还看不到管理页。下面按**你看到的那句话**来查。日志在 `<安装卷>/@appcenter/nasscreencompanion/@appdata/info.log`（应用中心里点「查看日志」也能看到）。

### 安装时被拦下

| 你看到 | 意思 | 怎么办 |
| --- | --- | --- |
| 「端口 8798 已被占用。请回到向导换一个端口再安装；**本应用不会结束占用该端口的进程**。」 | 你要的端口上已经有东西在跑 | 回到向导换一个端口。想知道占用者是谁，可以用「诊断」页（应用已经在跑的话）或 `ss -ltnp` 看一眼——**本应用不会替你去杀它** |
| 「未找到 python312 运行时（依赖应用可能还没装好）」 | 依赖的 Python 应用没装 | 先在应用中心装 `python312`，再装本应用 |
| 「检测到 8799 上有服务（应为开发版采集器）」 | 只是提示 | 不需要处理。两者可以并存，本应用用 8798 |

### 启动成功、但应用中心里点开是空的

这时**遥测接口是好的**（开发板照常读数据），坏的只是管理面。启动日志里会有这两句：

```
服务已启动，但管理面 Socket 没有出现：…/target/app.sock
应用中心里点开本应用会打不开，请看 info.log 里的绑定失败原因。遥测接口不受影响。
```

原因通常是 target 目录不可写，或者路径过长。`info.log` 里有具体的 errno。**开发板不受影响**，不用急着卸载。

### 启动了但读不到数据

先看管理页「诊断」标签页——它会逐项报告：

- **网关 Socket / Socket 权限**：管理面本身是否正常
- **遥测端口**：实际监听在哪个端口
- **鉴权模式**：是配对令牌还是内网免令牌
- **遥测面 TLS**：启用/关闭/失败，失败时会写出原因
- **首次取证书通道**：明文只放行 `/api/v1/identity`
- **运行用户**：真正跑着的 uid（应该是专用包用户，不是 root）
- **开发版端口 8799**：只报告，不触碰

### 「进程存在（pid …）但端口 … 无响应」

`main status` 会这么报（退出码 1，中间是实际的 pid 和端口号）。多半是端口被别的东西抢了，或者进程卡在启动中。看 `info.log`。

停止时如果优雅等待（10 秒）超时，会升级到 SIGKILL；**发完信号之后还会再看一眼**，
确认进程真的没了才说「已停止」。万一它卡在不可中断状态（D state）杀不掉，你会看到
「进程 … 在 SIGKILL 之后仍然存在」，`stop` 返回非 0——这时端口可能还被占着，
用 `ps -p <pid> -o pid,stat,cmd` 看它的状态。**不会出现"说停了其实还在跑"。**

## 数据来源与运行身份

| 数据 | 来源 |
| --- | --- |
| CPU / 负载 / 进程数 | `/proc/stat`、`/proc/loadavg` |
| 内存 / 交换 | `/proc/meminfo` |
| 网络速率 | `/proc/net/dev`、`/proc/net/route` |
| 卷容量 | `/proc/mounts` + `statvfs` |
| 阵列 | `/proc/mdstat` |
| 磁盘 IO | `/proc/diskstats` |
| 温度 | `/sys/class/hwmon/*/temp*_input` |
| 容器（可选） | `/var/run/docker.sock`，只调 `GET /containers/json` |

运行身份是**专用包用户**（`run-as: package`），不是 root。所有读取都是只读的；读不到的段会标注状态而不是静默给 0。**采样**的每段状态是 `ok` / `stale`（本次失败、沿用上一份旧值）/ `missing`（来源不存在）/ `denied`（权限不足）/ `error`（读到了但解析失败）/ `disabled`（被配置关掉，比如容器）；**能力矩阵**里每段还有 `partial`（部分可读，比如只有一部分温度传感器读得到）。

## 开发板侧的接口

供自研屏幕设备使用，三个端点：

- `GET /api/v1/health` — 存活探针
- `GET /api/v1/status` — 当前状态快照
- `GET /api/v1/history` — 最近若干采样

首次取证书：在**同一个端口**上，明文连接只放行 `GET /api/v1/identity`（返回证书 PEM），其余任何路径一律 403——因为设备在固定证书之前建不了 TLS。证书是公开信息，这一步不泄漏新东西；信任仍然建立在上面那次**人工指纹比对**上。

## 怎么打包

```sh
bash nas/fpk/build.sh
```

**别直接跑 `fnpack build`**：它会把包目录里的一切塞进包里，包括开发机上跑过服务端之后留下的 `__pycache__/*.pyc`（本机 Python 版本的字节码，而 NAS 上是 python312）。`build.sh` 会先清理、再打包、打完立刻扫一遍产物。

## 本地怎么验

```sh
nas/fpk/test_lifecycle.sh          # 打包 + 按真机布局解开 + 走完整生命周期（142 项）
bash tools/test_report.sh          # 跑全部检查并生成 docs/fnos-companion-test-report.md
```

装机之后、接板子之前，建议先跑：

```sh
python3 nas/fpk/board_sim.py --host <NAS-IP> --port 8798 --pair-code <六位码>
```

它把开发板配对时的五步 HTTP/TLS 序列原样走一遍（含"固定一张别的证书必须握手失败"这类否定断言），**不用等硬件**就能确认 NAS 这一半在你的网络里是通的。

配对成功后它还会顺手核对**板子要读的那 49 个字段，这台 NAS 是不是都给全了**——在开发机上这一步只能对着采集端源码猜（macOS 没有 `/proc`、`/sys`），在你的真 NAS 上会全部走真实响应。结尾会告诉你下一步该干什么。
