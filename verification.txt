3. 被审计基线 d84039f 为什么不能整树构建（补丁无关）
----------------------------------------------------

在 d84039f 树上（候选补丁已应用，fnos_ui.c 未被改动）执行工程入口构建：

    FNOS_IDF_ENV=/Users/llll/code/esp/use-esp-idf-5.5.3.sh ./idf.sh build

    components/fnos_monitor/fnos_ui.c:4299:35: error: array subscript -1 is below array
      bounds of 'lv_obj_t *[5]' [-Werror=array-bounds=]
     4299 |     lv_obj_update_layout(s_ui.page[idx]);
    components/fnos_monitor/fnos_ui.c:104:15: note: while referencing 'page'
      104 |     lv_obj_t *page[FNOS_UI_PAGE_COUNT];
    make failed with exit code 2

该文件在补丁树里与 d84039f 逐字节一致（`git diff --stat -- components/fnos_monitor/fnos_ui.c`
无输出），所以这是基线自带的问题，不是本次改动引入的。追加以 `-D CMAKE_C_FLAGS=-Wno-error=array-bounds`
重配后错误不变（IDF 的组件级 `-Werror` 在 CMAKE_C_FLAGS 之后生效，覆盖不掉），因此**没有**
在 d84039f 上得到完整固件。

同一棵树上，本次改动涉及的 C/C++ 单元逐个编译通过（2026-10-10 11:24–11:25）：

    fnos_pair.c.obj / fnos_data.c.obj / fnos_snapshot.c.obj   → 已生成
    esp-idf/main/CMakeFiles/__idf_main.dir/main.cpp.obj       → 已生成

并且配置阶段正常：该树 sdkconfig 里 `CONFIG_IDF_TARGET="esp32p4"`、
`CONFIG_SLAVE_IDF_TARGET_ESP32C6=y`、`CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM=10` 都在。
这正是报告 §6 那句提醒的实测依据——直接 `idf.py build` 而不走工程入口时没有导出
`ESP_IDF_VERSION`，esp_wifi_remote 的 `Kconfig.idf_v$ESP_IDF_VERSION.in` 会消失，
esp_hosted 随即报 `#error "Unknown Slave Target"`；用 `./idf.sh` 就不会。
