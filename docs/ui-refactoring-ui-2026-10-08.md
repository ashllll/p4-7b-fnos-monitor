# Refactoring UI 视觉优化与验证

本轮在已验收的 Device 风格和动效上继续优化五个 NAS 页面及配对、Wi-Fi、诊断覆盖层。
实际实现是 C/LVGL；开发工程为 `p4-7b-fnos-monitor`，资料仓中的示例没有改动。

使用 [gnurio/refactoring-ui-plugin](https://github.com/gnurio/refactoring-ui-plugin)，
读取版本 `00781eab1dde7fdb720d63f8d6c8148bf5835a31` 的 `meta-refactor-ui`、
`establish-visual-hierarchy`、`manage-color-contrast`。
按总评技能的十项分类检查，重点落实层级和对比度；其余分类结合实际版面定向判断。
所有修改复用原生字体、颜色令牌和自适应布局。
后续卡片间距整改使用同版本的 `apply-consistent-spacing` 技能。

## 问题与处理

| 检查角度 | 原问题或现状 | 本轮结果 |
| --- | --- | --- |
| 视觉层级 | CPU 当前值不显眼，系统页巨大装饰标题占位 | CPU 提升到现有 32px 字级，紧凑视口使用 20px；系统标题改为实际采集状态 |
| 字体尺度 | 导航和主卡辅助内容偏小 | 导航使用 16px；主卡辅助文案按视口在 12/16px 间适配 |
| 色彩系统 | 按钮填充色和文字色缺少成对语义 | 增加 `on_primary`、`on_danger`，四主题分别设置合适前景 |
| 间距 | 系统空告警和卡片内边距挤占列表空间 | 使用已有 4/8px 间距级别；空告警高度由字高和卡片结构计算 |
| 按钮层级 | 配对确认的浅桃色底配浅色文字 | 修正主按钮及按下态文字，保留边框与位移反馈 |
| 视觉杂讯 | 重复英文标记、强边框、列表随序号逐渐变暗 | 去掉冗余标记，减弱普通边框，列表使用统一底色 |
| 空状态 | 零告警的大块空白 | 收缩空告警卡；未采集、旧值、权限不足仍分别显示 |

| 对比度 | 夜间容量数值、主卡小字、列表副文、确认按钮偏暗 | 修正前景与背景；全部稳态样例按 4.5:1 检查 |
| 相关内容分组 | 系统清单显示面积不足，列表重排后顺序翻转；网络长接口名挤压统计分栏 | 释放空告警空间，保留采集器顺序；网卡信息均衡分栏，标识采用 16px 字级 |

800×480 按实际高度使用双列卡片和滚动；1280×800 可展开更多完整行。
温度页依旧由用户手动展开具体设备，定时采样只更新读数。
系统“无采集告警”仅表达采集器未上报告警，不推断所有硬件都正常。

共享列表重排原来倒序取出列与行，再以追加方式放回池中，改变了阅读顺序。
现在正序恢复并插到新行之前，无需额外分配；新增容器后也保持原采集顺序。
预览中另修正健康阵列样例，使 `ok`、成员数、同步进度和 `clean` 文案相互一致。
健康网络样例使用协议允许的最长 15 字符匿名接口名，覆盖真实设备发现的分栏空间问题。
接口名保留完整数据并按列宽显示，读数仍使用 20px 字级，吞吐图区获得更多高度。

## 清单可读性下限（2026-10-09 迭代二）

反馈原文是"部分卡片实在是太小了 没法看清信息 上下过窄"。实测（1024×600，`PREVIEW_BANDS_AT=02-live`）：
存储页三张卡的条目池各只有 55–59px，正好是一行（条目高 59、行距 8）；系统页的容器与硬件温度两卡
同样只露一行；首页"存储容量"卡的卷条池只有 25px，比一行还矮。四个几何审计一个都没报——"池里只露
一行"完全合法（内容多时本来就允许滚动），所以这类"太窄"一直没人拦。

做法（`components/fnos_monitor/fnos_ui.c` 的 `inventory_sections()`）：

- 行高、行距、列数一律**实测**（条目高度 + `uk_pool_cols()`），不读坐标：重排之后（尤其是非活动页）
  条目的 coords 可能还是上一次布局的旧值。
- 卡的最小高按"池承诺 `UK_LIST_MIN_ROWS`（2）行"算，卡的内容高按"池把全部条目摊开"算；两者都基于
  **实测的卡内开销**（当前卡高 − 当前池高，标题、内外边距、隐藏的空态占位都算进去），量不出时退回
  手算的 chrome。手算 chrome 会漏掉这些占位——p1 的池正好少 8px，第二整行被切掉。
- 用 `LV_SIZE_CONTENT` 量卡不行：`grow=1` 且 `min_height=0` 的子对象（空态盒子）会让卡塌成标题高，
  里面的文字反而溢出（`audit_bounds` 报 child out of parent）。
- 池的 `min_height` 停在"2 行"这个硬下限，不是内容全高：条目多的池不该把卡顶得比视口还高。
- 容器在内容高于视口时**必须**从 `grow=1` 退成定高：父层会裁掉超出部分，而页级滚动的范围是按容器
  自己的高度算的，被裁的那截连滚都滚不到。
- 首页那条紧凑对比条按 **1 行**判、1 行保：它的预算装不下两行（卡片高定死 130，内容池 86 里已经有
  大数字和值条）。

新增 API（`components/fnos_monitor/ui_kit/uk.h`）：`UK_LIST_MIN_ROWS`、`uk_list_mark()` / `uk_list_is()`
（清单标记，`LV_OBJ_FLAG_USER_3`）、`uk_list_readable_min(list, items)`、`uk_list_content_min(list)`。
（本节最初的版本只给 p1/p3 的几个池显式打标、池不自动打标；下一节把它推广成全页统一口径。）

新增审计（`tools/preview/preview.c` 的 `audit_list_floors()`）：清单容器的高度必须够它承诺的项数，
判据与布局共用 `uk_list_readable_min()`。这是"卡片太小"的**正面**判据：几何审计只查"跑出父对象"，
"只露一行"完全合法，所以此前四个审计都不说话。

结果：p1 的存储卷卡与阵列健康卡各完整露出 2 行（卷 6 条、阵列 4 条），第三张磁盘活动卡落到折叠线
以下（页可滚、卡片完整，不再是半截卡）；p3 的容器服务与硬件温度各 2 行。内容高于视口时容器定高、
页级滚动接管。`audit_list_floors` + 四项几何审计 + 84 帧静态矩阵 + 对比度 4.5:1 全部通过。

已知且**先前就存在**的限制：`PREVIEW_SIZE=800x480` 的整轮矩阵在 `verify_reasons()`（配对失败原因
必须都画在屏幕上）处 abort；把工作区改动 stash 掉、只编提交版 c81b8fc 复现同一断言，与本轮改动无关。

## 全页推广（2026-10-09 迭代三）：清单下限覆盖每一页

反馈原文："所有的页面都需要这样处理"（承接"部分卡片实在是太小了 没法看清信息 上下过窄"）。
上一节只给 p1/p3 的几个池显式打了标 —— 打标是**调用方的记忆**，漏一处就等于没审计。这一节把
"哪些容器算清单"变成类型自带：

- `uk_pool_create()` 建出来的池自动是清单（默认承诺 `UK_LIST_MIN_ROWS` 项）；`fnos_ui.c` 的
  `scroll_col()`（告警那种长短不一、还要换行的列）同样在建的时候自动打标。新加的列表不需要
  任何人记得打标。
- 承诺几项由容器自带（`uk_list_promise()`）：池与滚动列默认 2 项；**可变高复合块**清单和
  **没有第二项空间**的紧凑条用 `uk_list_mark_one()` 降到一整项 —— 温度页设备池（展开后一块
  200~260px 高）、首页那条紧凑卷条（两行会把这排磁贴顶高 29px、把上面的卡挤出可视区）。
- 单项本身就比视口高时（设备块展开态）"露一整项"物理上做不到：审计对这种**块清单**免检
  （判据是 `uk_list_item_max(o) > 容器高`，且只对承诺 1 项的清单生效；行清单不受影响 ——
  p0 曾把 25px 的行塞进 21px 的池，那种情况照报）。块内文本不被裁由 `audit_bounds` 与对比度兜底。
- 布局侧：`inventory_sections()`（p1/p3）与 `overview_layout()`（首页卷条）都改成读
  `uk_list_promise()`，下限公式仍只有 `uk_list_readable_min()` 一处；审计侧
  `audit_list_floors()` 同样读它 —— 布局与审计不可能各自演化出不同口径。
- 新增 `uk_list_item_max()`（清单里最高的一条）；`uk_list_readable_min()` 的形参由 `rows` 改名
  `items`（它一直只懂"项"，不懂"行"）。

## 卡片边界按内容定高（2026-10-09 迭代四）

要求是"卡片边界随字符串自动缩放，所有界面都要有"。根因两条：

- 卡高一直是**视口**算出来的，不是内容算出来的：`inventory_sections()`（存储页/系统页共用）把容器
  高度夹在实测可用高上（`target = LV_MAX(min_total, LV_MIN(h, desired))`），`uk_card_flex(card, grow>0)`
  则把卡直接写成 `LV_PCT(100)` —— 内容少时卡片留白，内容多时卡片被页边界切掉。
- 温度页的页根本不是可滚页：`build_p4()` 自己摆了 flex 容器并显式
  `lv_obj_clear_flag(page, LV_OBJ_FLAG_SCROLLABLE)`，于是长出来的卡片连滚都滚不到。

改法（全部在 `components/fnos_monitor/fnos_ui.c`）：

| 位置 | 改动 |
| --- | --- |
| `inventory_sections()`（存储页 + 系统页） | 卡高 = 池把全部条目摊开需要的高度（行内取最高者），容器跟着撑高；一屏装不下交给页级滚动 |
| `build_p4()` | 页改用共用的 `ui_page()`（可滚）；`uk_card_flex(temp_card, 0)` + 池 `grow 0 / LV_SIZE_CONTENT` |
| `build_p5()` 与 `alert_health_sync()` | 告警卡按明细内容定高；空态盒子给真实行高（内容高卡里 `flex_grow` 撑不出高度，字会跑到卡外） |
| `build_p2()` | 网口卡按内容定高，余量全给趋势图 |

刻意**不**按内容定高的两处：总览页的磁贴/曲线（图表本就吃满余量），以及配对 / Wi-Fi / 诊断三个整页
浮层（固定页脚的设置面板）。
