# KKUI 监控界面重构 v8「仪器感 + 信息密度」

日期：2026-10-05。承接 [ui-redesign-v7.md](ui-redesign-v7.md)，本轮只改视觉语言与信息密度，
不动数据层、不改导航结构、不引入新依赖。

## 这轮要解决什么

用户原话：*"信息密度是否还能再提升点 ui 现在还是有点简陋不够科技风"*。
两个诉求分别对应两个真问题：

1. **简陋**——v7 完全靠"表面色阶"分层（卡片纯色 `KK_S1`、无边框无阴影），在 169.5 PPI 的
   反光 IPS 屏上，卡片边界要靠色差去猜，缺少仪器感。
2. **密度**——数据层早就返回了 `cpu.load1/5/15`、`cpu.procs`、`mem.swap_*`、`net.rx/tx_total_gb`、
   `http_ms`、`ok_count/fail_count`、`uptime_s`，界面一个都没用；同时 P0/P2 各有一张
   924×80 的"底注"卡只放两行字。

## 硬约束：密度只能靠"少废话"，不能靠"缩字号"

按 16 arcmin 的字高底线换算本屏（169.5 PPI，1px = 0.150 mm）：50 cm 观看距离下，
字高需要 15.5px（≈22px 字号），70 cm 则需要 ≈31px。**所以"提密度"在本项目里的含义固定为：
把有限的像素用来多放一条真正有信息量的数据，而不是把已有文字调小。**

- 字号阶梯维持 v7：主数值 44px、网络混排 30px、标签与次要值 18px、明细 15px、脚注 13px。
  新增内容一律落在 13–18px，主数值不许为了塞内容而降级。
- 对照基准：IBM Carbon 数据表 xs 行高 24px / sm 32px；Grafana 栅格高度单位 30px。

## v8 视觉令牌（`components/fnos_monitor/kk_ui/kk_theme.h`）

| 令牌 | 值 | 用途 |
|---|---|---|
| `KK_S0` | `0x0E0F11` | 嵌槽底：分组内凹、指标格、迷你图底（比画布更深） |
| `KK_SURF_T` / `KK_SURF_B` | `0x272A2F` / `0x17191C` | 卡片"微浮起"竖向渐变：顶亮底暗，替代阴影做层次 |
| `KK_LINE` | `0x2E3238` | 卡头下沿与密集区行分隔（比发丝线亮一档） |
| `KK_EDGE_OPA` / `KK_EDGE_STRONG` | `26`(10% 白) / `45`(18% 白) | 卡片外沿发丝边 / 焦点卡外沿 |
| `KK_GLOW_W` / `KK_GLOW_OPA` | `10` / `140` | 光晕宽度与不透明度（LVGL 的 shadow 0 偏移即光晕） |
| `KK_ROW_H_METRIC` / `KK_ROW_H_DENSE` | `54` / `44` | 指标行 / 密集行高度台阶 |

关键实测结论（试片 `tools/preview/style_proof.c`，同款 Kconfig + RGB565 出图）：

- **1px 发丝边的白色不透明度低于 10% 会被 RGB565 量化直接吃掉**——7% 完全看不见，
  10% 是能看见的下限，18% 明确可见。所以卡沿取 26（≈10%），焦点取 45（≈18%）。
- 卡片竖向渐变在 565 下干净成立，不会出色带；而大面积渐变仍受"总面积 ≤ 全屏 25%"的限制。
- 光晕用 `shadow` 且 offset 为 0：8–10px 的小目标配 `width=10, spread=2, opa=140` 能得到
  均匀一圈，不会糊掉旁边的字。
- **不做**背景网格/扫描线：1px 纹理与像素栅格拍频会出摩尔纹，且每帧全屏合成太贵；
  也不做 1px 竖细线（斜视会消失、亮度不均）。样张里留了对照，见 `style-proof.png` 底部。

## 视觉改了哪些

- **卡片表面**：`card_surface()` = 竖向渐变 + 1px 白发丝边，`mk_card()` 统一走它；
  夜间模式保留同一套结构，只把两档表面压到 `0x141619`/`0x090A0B` 并把发丝边降到 0。
- **导航选中态**：从"整块品牌蓝底"改成"左侧 3px 品牌蓝条 + 同色光晕"。
  理由是整块蓝底让导航比数据本身更抢眼，也与"蓝色表示可交互"的约定冲突。
- **状态点光晕**：顶栏在线/离线/等待与网络页网卡点用 `kk_glow()`；
  但文字仍是主编码，光晕只是冗余强调（反光屏上光晕会糊，不能单独承载状态）。

## 滚动条与文字的净间隙（回归看门狗）

v7 遗留缺陷"右对齐状态列压在滚动条上"已修（`KK_SCROLL_INSET` / `KK_SCROLL_GAP` 令牌），
并有像素级看门狗守着：`node tools/preview/scroll_gap.js tools/preview/out`
（27 处滚动条全部要求 内容→条 ≥8px 且 条→内缘 ≥4px，非 0 退出即回归）。
注意 v8 给卡片加渐变后，该脚本一度报 27/27 假阳性——原因是"拿卡片一个点当全局底色"在渐变卡上不成立；
现已改为逐行基线 + 扫描窗从卡头下方起算，机制与三个坑写在脚本注释里。

## 配对页（v8 期间新增的第 5 个整页卡）

导航最下方多了一个 `配对` 入口（`s_ui.pair_btn`，620×… 的 rail 按钮），点开是一张盖在
系统页上的整页卡 `pair_build(page)`。它不是第五个导航页——真正的阶段由 `fnos_pair` 的
状态机决定（`FNOS_PAIR_UNPROVISIONED / FETCHING / CONFIRM / PAIRING / PROVISIONED / FAILED`），
UI 只读 `fnos_pair_view()` 的快照，**不在本地再实现一套状态机，否则两边会漂**。

界面元素：标题 + 一行操作提示 + 6 位配对码槽位 + 数字键盘（1–9 / 删除 / 0 / 确认）+ 指纹核对态
（4 行 × 每行 8 字节的 SHA-256、CN 与到期日）、`接受并配对` / `取消` / 两步确认的 `解除配对`。

信任模型（细节见 `components/fnos_monitor/fnos_pair.h` 的注释）：证书由板子自己从服务器取回并
自算 SHA-256，指纹显示在屏上由用户与 NAS 管理页比对；**确认之前不发任何带令牌的请求，也不采信
服务器 JSON 里的指纹字段**——否则中间人同时伪造证书和那个字段就能骗过肉眼比对。没配对过的板子
退回编译期默认参数（明文、无令牌），行为与配对功能存在之前完全一致。

## 主任务栈 3584 → 16384（启动崩溃修复，2026-10-05）

加了配对整页卡之后，固件**启动即崩溃、每 4.6 秒重启一次**：

```
Guru Meditation Error: Core 0 panic'ed (Stack protection fault).
Detected in task "main"    Stack pointer: 0x4ff6d3c0
                           Stack bounds: 0x4ff6d3c8 - 0x4ff6e3c0
```

符号化崩溃 PC 落到 `heap_caps_aligned_alloc_base → heap_caps_malloc`，也就是 LVGL 建构件
分配内存那一步。默认 `CONFIG_ESP_MAIN_TASK_STACK_SIZE=3584`（3.5 KB）对
`app_main → fnos_ui_create() → 建四页 + 配对整页卡 → lv_obj_create → lv_malloc`
这条链太薄；LVGL 自己的任务栈本来就配了 12 KB，主任务没有对齐它。

修法：`sdkconfig` 与 `sdkconfig.defaults` 都写 `CONFIG_ESP_MAIN_TASK_STACK_SIZE=16384`
（defaults 里也写一份，避免将来重新生成 sdkconfig 时又退回 3584）。
修后启动日志：`fnos_ui: ui created (pages=4)` → `main: boot complete`，38 秒内 `poll ok=30 fail=0`，
串口里 Guru/panic/assert 命中 0 次。

**教训：在 ESP-IDF 里往 UI 初始化路径上加构件是有栈预算的**。页面/整页卡越加越多时，
"能编译过"和"能跑起来"之间差的就是这条主任务栈——真机一上电就见分晓，预览（主机上跑，
栈是 MB 级）永远测不出来。

## 配对界面的重排（用户："都要重排，且 UI 按钮设置一定是要非常清晰的"）

改前是一张"卡头 + 左栏一整段说明 + 右边一个盒子"的连续文本块，按钮没有分量差、
位置也靠"互斥显示"侥幸不重叠。现在按**四模块 + 操作条**排：

| 位置 | 模块 | 内容 |
|---|---|---|
| 卡头 0..76 | 标题 + 一句话状态 + 结构线 | `与 NAS 配对` / `核对证书指纹`，第二行随阶段换 |
| 左栏 16,80 336×328 | ① 三步指引 | 序号徽章 + 每步一句"做什么"，`WRAP` 折行 |
| 右上 364,80 544×124 | ② 配对码 | 6 个独立槽位（已输入=主文本色、未输入=`-` 弱化）+ 一句"码从哪来" |
| 右下 364,212 544×216 | ③ 数字键盘 | 3×4，键 160×48、行距 50；数字用 `num_22`，删除/确认用 `cjk_18` |
| 右上同位（阶段互斥） | ④ 指纹块 | 4 行 `num_30` 指纹 + `CN/到期` + "接受之后会发生什么" |
| 操作条 428..498 | ⑤ | 关闭 528 ┊ 解除配对 744 ┊ 主操作 920（各 148~160 宽，52 高） |

**内部预算算法（排布前先算，别凭感觉给高度）**：卡片 522 高 ⇒ 内容预算
`522 − 24 边距 = 498`。然后卡头 0..76 ┊ 模块区 80..416 ┊ 操作条 436..498。
这次吃过一次亏：操作条按 y=458 排，整排落到卡片外，是预览新加的
`child out of parent` 断言（`tools/preview/preview.c` 逐层检查子对象越出父对象 2px）
抓出来的 —— 纸面上"看着差不多"，探针一跑就现形。

## 左栏只有一块地方（真机暴露、预览盲区）

配对卡的左栏（x16 w336）只有一块地方，能进去的只有两样东西：**三步指引**（输码/失败阶段）
和 **状态说明**（其余阶段）。两者必须互斥。

原来不是这样：状态说明的显示条件是"`v.msg` 非空"，而未配对时 `v.msg` 就是
`未配对：用编译期默认地址` —— 于是在"输码"阶段它和"三步完成配对"同时出现，两段文字
**叠在同一块地方**，真机照片上一眼可见。

**预览为什么全绿也没发现**：`tools/preview/preview.c` 里的 `fnos_pair_view()` 桩件把
`msg` 固定成空串，而设备端 `fnos_pair_init()` 会写 `未配对：用编译期默认地址`。
桩件行为与设备不一致，预览的绿灯就是假的。修法两条：

1. 桩件的 `msg` 按设备的行为补齐（未配对 = `未配对：用编译期默认地址`，已配对 = `已配对`）；
2. 预览新增断言：输码阶段**不能**同时出现状态说明。

顺带把交互提示（`配对码是 6 位数字，还差 3 位` 这类）从"挤进左栏"改成挂在**右侧配对码块**
的最后一行（橙色 `KK_WARN`）—— 它和"配对码 / 槽位 / 码从哪来"讲的是同一件事，
放一起更好读，也不必再和"三步指引"抢地方。新增预览态 `07-pair-hint.png` 覆盖它。

## 按钮分级（`BTN_PRIMARY / SECONDARY / NEUTRAL / DANGER`）

一条 `btn_style(b, kind, f, txt_rgb, bg_rgb)` 统一落地，**参数顺序与 `mk_btn`
一致（先文字色后背景色）** —— 这不是洁癖：曾经写成 `(…, bg_rgb, txt_rgb)`，
而调用点按 `mk_btn` 的习惯传了 `(KK_T1, KK_BLUE)`，于是主按钮的背景被当成了 0，
屏幕上"接受并配对"变成一块纯黑。参数顺序不一致时编译器不会报错。

- `BTN_PRIMARY` 蓝底白字，**整屏对比最强的一块**，永远待在右下角同一位置（换阶段只换
  文案不换位置）。
- `BTN_SECONDARY` 深底 + 25% 白描边：看得出边界，但不抢主操作。
- `BTN_NEUTRAL` 卡片同档底色 + 14% 白描边。
- `BTN_DANGER` **不常驻红底**，只在"解除配对"二次确认武装后才变红——红底常驻会把
  "关闭/取消"这种安全出口也染成警告色。
- 每个按钮都响应 `LV_EVENT_PRESSED / PRESS_LOST / RELEASED`（叠 11% 白 + 下沉 1px）：
  触屏上不动的按钮分不清"没按到"和"按了没反应"，这是"清晰"的另一半。
- `KK_EDGE_CTRL 64`（25% 白）是交互件边界下限——8% 发丝边在 565 下太弱，
  "看得出这是一块能点的东西"比"优雅"重要。

**参数顺序这条错误又复发过一次**：`pair_pad_restyle()` 的三处调用点没跟着改，
于是键盘的「确认」键背景被设成 `KK_T1` 的白色 —— 暗底上一块纯白，非常显眼。
现在 `KK_PROBE_KEYS=1` 会把键盘上三个非数字键的底色跟期望值比对并打印 OK/MISMATCH。

## 渐变在本屏禁用（用户："配对界面的 UI 背景色是花花绿绿的"）

**根因是 RGB565 量化，不是绘制 bug。** `KK_SURF_T 0x272A2F → KK_SURF_B 0x17191C`
只差 16 级亮度，铺在 470px 高的卡片上只量得出 **7 条色阶**；而相邻色阶的舍入误差落在
**不同通道**（阶差依次 −G、−B、−R、−G…），于是屏幕上出现的不是"深浅渐隐"，而是
一条条偏绿/偏蓝/偏红的横条。LVGL 的渐变不做抖动，RGB565 也没给抖动留余量。

处理：**全屏取消渐变，一律纯色**。层次只能靠三样东西堆——表面色阶、发丝边、分隔线。
令牌随之改名：`KK_RAIL_N 0x141518` / `KK_RAIL_DAY 0x1C1F22` / `KK_NAV 0x232629` /
`KK_NAV_SEL 0x272A2D`（选中态仍是"纯色 + 21% 品牌蓝叠加"，纯色后只需设 `bg_opa`），
卡片表面用原渐变的中间调 `KK_SURF_T 0x1F2226`，`KK_SURF_B` 已退役。

## 左导航栏的模块化分层（用户反馈"目视一点不清晰"）

改前：整条 rail 一个纯色 KK_S1、导航项背景透明、标签 KK_T3 —— 模块之间没有任何边界，
眼扫过去是一列糊在一起的灰字。

改后（`theme_apply()` 一处落地，建树/换页/夜间/配对状态全走它）：

| 层 | 表面 | 说明 |
|---|---|---|
| rail 底 | `KK_RAIL_DAY_T 0x24272B → KK_RAIL_DAY_B 0x141619`（夜间 `0x1A1C1F → 0x0B0C0E`） | 比卡片深一档 = 内凹槽 |
| 导航项 | `KK_NAV_T 0x1E2124 → KK_NAV_B 0x141619` + 10% 白发丝边 + 8px 圆角 | 浮起一档，成为可辨认的"块" |
| 选中项 | `KK_NAV_SEL_T 0x2E333A → KK_NAV_SEL_B 0x1F2327`，**叠 21% 品牌蓝**（`bg_opa` 与 `bg_grad_opa` 都设 `KK_NAV_SEL_OPA 54`） | 蓝只做叠加不遮字，再抬一档 + 18% 边 + 左侧 3px 蓝条与光晕 |
| 图标/文字 | 选中：`KK_BLUE_TXT` / `KK_T1`；未选中：两者都 `KK_T2` | 改前未选中是 `KK_T3`，与 rail 底对比不足，"不清晰"的主因 |

另外做了三件事：

- rail 右沿一道 `KK_EDGE_RAIL`(8% 白) 单边发丝边，把栏和内容区切开。
- 导航区与配对区之间、配对区与底部 NAS 之间各一道 `KK_LINE` 分隔线——分组靠边界，不靠间距猜。
- 配对入口从"整块橙色标题"改成"主文本色标题 + 左侧状态点"（未配对橙 `<KK_WARN>` 带光晕 /
  进行中蓝 / 已配对主文本色不发光）。它是**入口**不是状态，拿橙色染标题等于把入口画成告警。

### 排版上踩到的两个坑（都会静默裁字，预览断言抓得到）

- **标签盒宽度**：15px 字号下 "已配对" 三个中文字要 45px，盒子给 40px 会被裁成"已配"。
  配对入口的标签盒定死 46px 宽（三个字的上限），x 定在 14，右侧才不会压到按钮边。
- **标签盒高度**：中文字体的行高远大于字号——`ui_font_cjk_15` 的行高是 **38px**、
  `ui_font_cjk_18` 是 **30px**。盒高小于行高时预览的 `text overflow` 断言直接 abort
  （`tools/preview/preview.c:332-338` 用 `lv_text_get_size` 比盒子尺寸）。
  改这批盒子时按"行高"给高度，别按字号给。

## 验收顺序：真机上电冒烟必须排在视觉验收之前

本轮犯过的错，记在这里当流程闸门（不是可有可无的建议）：

1. **主机预览全绿 ≠ 固件能用**。预览在 macOS 上跑，栈是 MB 级；真机 main 任务只有 3.5 KB
   （已改 16 KB）。上面那次栈溢出就是"预览 32 张 PNG 全绿 + 断言全 PASS + 看门狗 0 处不合格"，
   而真机每 4.6 秒重启一次。**改 UI 结构（加页面 / 加整页卡 / 加构件）后，先烧录、先看串口，
   再做视觉验收**——反过来的话，视觉验收花的时间可能全白费。
2. **往 UI 初始化路径加构件，要顺带算一次栈预算**（v4 那轮 `fnos_dash_view_build` 单函数
   11392 B 栈帧也是同一类问题，见 `docs/` 里的 v4 排障记录）。量大时用
   `riscv32-esp-elf-gcc -fstack-usage` 逐函数出栈帧，别靠猜。
3. **不要把判定阈值或扫描窗口改到"指标变绿"**。看门狗的用法是用它去改代码，不是拿它去改进度条：
   本轮 `scroll_gap.js` 的扫描窗和基线算法确实是错的（真 bug，必须修），但当时的动机是
   "让它别报红"，一旦养成这个习惯，看门狗就再也不能证明任何事了。改检测逻辑要先把
   改前的真阳性（内容越过条子左缘，间隙 -1~+2px）复现出来当回归样本。
