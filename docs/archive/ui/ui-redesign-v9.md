# UI v9：版面合同（消除"错位"）

起因：用户反馈"UI 设计完全是错位的，全面整改"。逐条量过之后，"错位"不是感觉问题，
是**四处真实的几何错误**加两类**没有单一来源的魔法数**。v9 的做法是把版面变成可验算的
合同，再用审计脚本守住它，而不是靠眼睛。

## 一、四处错位与根因

| 症状 | 根因 | v9 的解法 |
| --- | --- | --- |
| KPI 卡里数值和单位的间距每张卡都不一样（4~64px） | 单位框按 `x = 16 + 132 + 4` 硬排，值一变宽单位就漂；曾把单位框改成定宽 48 右对齐，结果 `MB/s` 被截成 `M…` | 值与单位**都左对齐**，间距恒为 `KK_INLINE`(4)：值框 120 + 单位框 64 |
| 折线图下面"CPU 37% · 峰51% 内存 63% · 峰67%"四块对不齐 | 那是"伪图例"：每格各自排版，左缘互不相同 | 改成**读数行**：点名贴左轴 `x=KK_PAD`，读数贴右轴右对齐 `x=w-KK_PAD` |
| 系统页状态行被压到规则线下面（重叠 2px） | 页头卡既有卡头标题"系统摘要"又有状态行，两个标题说同一件事 | 删掉卡头标题：状态行本身就是标题 |
| 配对页步骤序号圆点与文字不成组、导航项之间有孤立小点 | 圆点与文字的 y 各自算 | 圆点与文字同 `y`，同组只用组内间距 ≤8 |

两条**更根本**的教训：

1. **行高才是版面的真实高度，字号只是名义值。** `lv_font_conv` 没有 `--line-height`，
   行高由字体度量决定，实测：`cjk_20→23 / cjk_16→19 / cjk_12→14 / num_44→52 /
   num_32→39 / num_20→24 / txt_15→18 / txt_12→15`。按字号排版必然挤或空。
2. **单位/数值这类"要显得对齐"的东西，不能靠右对齐凑**，要给它固定的盒。
   右对齐看着整齐，实际是"12.2"离"MB/s" 40px 而"37"离"%" 130px。

## 二、版面合同（`kk_ui/kk_layout.h` 是唯一来源）

```
间距阶梯  4 / 8 / 12 / 16 / 24 / 32          外边距 12，卡片间隙 12
纵向恒等式 三块页 12 + H3(64) + 12 + HT(160) + 12 + HM(272) + 12 = 544
           两块页 12 + H2(96) + 12 + HLA(224) + 6 + HLB(182) = 532
卡片内边距 横向 16、纵向 12                    卡片圆角 8（不许更大）
列表行     行高 60 = 主行 y+8、副行 y+26、进度条 y+54，数值列右距 16
KPI 卡     标签 y+14 / 值 y+36 / 副行 y+96（网络页 112）/ 进度条 y+142
```

**页面里不许再出现魔法数**：所有 x/y/w/h 从 `KK_*` 取。哪条不够用就先改合同。

行高 60 而不是常见表格行高 44：本屏的行里有**三样**东西（主行 `cjk_16`、副行
`cjk_12`、可选进度条），44 装不下；硬塞会让副行贴条、条压行边。

存储页两块为什么是 224/182 而不是"等高 206"：等高会让上面的卷列表只剩 1.8 行；
224/182 是"下块装 3 行（3×60=180 + 卡头 36 + 内边距 8 = 224 反推）"的结果。
**块高由内容反推，不是先定块高再塞内容。**

## 三、颜色与可读性红线

- 卡面 `#1F2226` 上的实测对比度：T3 8.35、绿 6.61、橙 6.82、红 5.03 —— 都可以；
  **T4 `#737C87` = 3.77、品牌蓝 `#006EFF` = 3.55，低于 WCAG 4.5:1，禁止用于 22px 以下**。
- 表面只保留四级（`#0E0F11` / `#131416` / `#1F2226` / `#2A2E33`）+ 分隔线 `#2E3238`。
- **不用渐变**：RGB565 量化会把低对比渐变切成"色相不对的条带"（用户报过"花花绿绿"）。
  层级靠表面色阶 + 发丝边 + 分隔线。
- 缩放：169.5 PPI、1px = 0.150mm；50cm 观看时 16 arcmin ≈ 15.5px 字高。
  **密度只能靠减行数，不能靠缩字号。**

## 四、守卫：三条自动化审计

改完 UI 跑 `bash tools/preview/run.sh`，它会做：

1. **几何审计** `audit_bounds`：子对象越出父对象、文本溢出盒、缺字形（豆腐块）、
   文本互相重叠。`PREVIEW_AUDIT_ALL=1` 跑完所有违规再退出（默认首错即停）。
   两条容易踩的规则：
   - 文本重叠比的是**字形盒**，不是标签盒 —— 否则一个 248 宽的副行和一个 64 宽的
     状态列本来不挨着，却因为"盒挨着"被判重叠，逼着人把版面改坏去迁就测试。
   - `visible_text()` 是**整串相等**比较，不是子串；刷新只发生在定时器里，
     点完导航要跑一拍 `vtick_advance(500); lv_timer_handler();` 再断言。
2. **滚动条看门狗** `node tools/preview/scroll_gap.js tools/preview/out`：
   判据「内容→条 ≥ 8px」且「条→卡片内缘 ≥ 4px」。卡片几何**从二进制读**
   （`PREVIEW_CARDMAP=1 build/preview` 让 `fnos_ui_dump_card_map()` 吐真实 coords），
   不许再手抄一张卡片表 —— 抄错一次报了 15 处假不合格，排查花了两小时。
3. **从未露面审计**：整棵树走一遍（含 HIDDEN），报出"一次都没被审计看过"的构件，
   基线 56（行池里用不到的那些）。新增的构件如果没有哪一步打开它，就会被抓出来。

像素级判读**读 PPM**（preview 直接写的帧缓冲），不要读 PNG：`out/*.png` 由
`ppm2png.py` 从 PPM 转换，曾经因为读到旧 PNG 误判"P2 文字巨大、卡片重叠"。
`bash tools/preview/run.sh` 会 `rm -rf out` 重生成，改完 UI 先跑它再读图。

## 六、改这个 UI 的顺序（照做就不会返工）

1. 改文案或字号 → `bash tools/gen_fonts.sh`（子集字库，缺字在预览里是方块）。
2. `bash tools/preview/run.sh` → 断言必须全 PASS。
3. `node tools/preview/scroll_gap.js tools/preview/out` → 必须 0 不合格。
4. 读 `tools/preview/out/*.ppm`（或 PNG）目视四页。
5. `./idf.sh build` → `./idf.sh -p /dev/tty.usbmodem* -b 460800 flash` → 串口冒烟。
6. 实机拍照复核（`<user-home>/.local/bin/capture-board`）。**预览绿不等于交付**：
   桩件必须与设备一致，单张照片也不足以证明无闪烁与数据新鲜度。

## 七、换设计而不换几何：配色与版面的可切换边界（2026-10-06）

用户问"是否还有别的 UI 设计方案"。可换的东西必须分成两类，混在一起就会重新长出"错位"：

**可以整套换（不动一行几何）—— 配色。** 颜色令牌已改成**运行时调色板表**
（`kk_ui/kk_theme.h` 声明结构 + 宏，`kk_ui/kk_theme.c` 放预置）。
令牌的名字没变，只是从"编译期常量"变成"读 `g_kk_pal` 的字段"，所以 200+ 处调用点一处没动，
换配色 = 改表。设备端 `CONFIG_FNOS_PALETTE`（graphite / abyss / phosphor，默认 graphite），
预览端 `KK_PALETTE=<名字>`；配色在建构件**之前**定下来（LVGL 样式是拷贝语义，建完再换不生效）。
防呆：`__attribute__((constructor))` 先把调色板装成默认值 —— 忘赋值会是全黑屏，
这种错误必须在结构上不可能发生。

**不能换（换了就是错位）—— 版面合同。** `kk_layout.h` 的间距阶梯、纵向恒等式、
行内位移、卡片内边距、滚动条净距那五组常量是几何唯一来源。要改设计只能**改合同再全页重排**，
不能在某页上"手工挪一下"，那正是 v9 要消灭的东西。

三条审计对配色同样生效，而且**换配色必须重跑**：`bash tools/preview/palettes.sh`
（三套配色 × 四页，逐套跑几何审计 + 滚动条净距 + 对比度，任一不合格就退非 0）。
这条纪律立刻救过一次：phosphor 把交互色设成琥珀 `#FFB000`，而 `KK_BLUE` 还兼着
左上角 App 图标块的底色，白字压琥珀只有 **1.83:1** —— 对比度审计直接拦下，改成蓝色收工。


## 八、v10：几何变成"推导出来的表"（2026-10-06）

v9 把坐标写进 `kk_layout.h` 的宏里，**换一块屏幕就要手改 31 个数字**。v10 把几何变成
一张按真实显示尺寸与数据条数解出来的表：

- `kk_ui/kk_metrics.h`：`kk_metrics_t KKM` + `kk_metrics_recompute(scr_w, scr_h)` +
  `kk_metrics_dump()` + `kk_trend_layout(card_h)`。
- `kk_ui/kk_metrics.c`：三条纪律写在文件头 ——
  1. **先写恒等式，再解未知量**。页面纵向：`body_h = margin + h3 + gap + [ht + gap] + hm + margin`。
  2. **缩放后必须落回设计阶梯**（`snap(v, lo, hi)` 取整到 2px 并夹范围）。
     只对**结果**取整，绝不对比例取整。
  3. **行高由"卡内要装几行"解出**，并夹在 `[44, 72]`。
- `kk_layout.h` 只剩与屏尺寸无关的常量（间距基准 12/16、圆角、屏幕标称尺寸），
  其余 31 个宏改成读 `KKM` —— **调用点一处未动**。

1024×600 当前解（`KK_METRICS_TRACE=1 ./build/preview` 可复现）：

```
h3=44 ht=160 hm=280 card_title_h=24
list_row=54 list_row3=56 h3col=473 hla=222 hlb=222
```

### 踩过的三个坑（都是"不报错的错"）

1. **顺序**：`hm` 依赖 `h3`，必须在 `h3` 之后算。曾经先用旧的 `h3=64` 算 `hm`，
   系统页摘要条长到 260，把三列卡压掉一半 —— 只有 `card overlap` 能抓。
2. **卡高必须由行数反推**：`卡高 = 列表顶 48 + n×行高 + 卡底 12`。
   先写卡高再算行高，第 n 行会被静默裁掉，几何审计看不见。
3. **行高的下限要把三段真实高度写进去**：`8 + 19 + 4 + 14 + 2 + 4 + 8 = 59`。
   行高 54 时副行后 7px 压在进度条上 —— **文字与图形重叠，几何审计抓不到**。

## 九、消耗空白（方案 A）：曲线长高 + 读数行贴绘图区

- `kk_trend_layout(card_h)` 统一算绘图区：`plot_y = 卡头 + 轴标行`、
  `plot_h = 卡高 − plot_y − 轴标行 − 读数区(2 行)`，`xaxis_y < 0` 表示这块卡排不下 X 轴标签。
- 读数行（`CPU 37% · 峰 51%`）紧贴绘图区正下方，不再压在卡底。
- 原来总览页图表卡的绘图区只有 33px 高、上下各 30px 死区；v10 后绘图区吃满可用高度。

## 十、补齐"采到了但界面没用"的字段

| 字段 | 落点 | 说明 |
|---|---|---|
| `cpu.procs` / `cpu.runq` | 总览页 CPU 卡副行 | `8 核 · 负载 1.42 · 队列 2` —— 运行队列 > 核数是过载信号 |
| `mem.swap_total_mb/used_mb` | 总览页内存卡副行 | `10.1 / 16.0 GB · 换 0.1/2.0G`（长写法会被静默截断） |

| `cpu.load5/load15` + swap + uptime | 系统页摘要条第二行 | `负载 1.42/1.18/0.96 · 进程 412 · 交换 0.1/2.0G · 运行 2d 07h` |

⚠️ **文案变长 = 字体要重生成**：`ui_font_cjk_*` 是**子集字体**，字符集从源码里扫出来。
新写一个汉字（如"队"）必须先 `bash tools/gen_fonts.sh`，否则预览直接报
`missing glyph U+961F`，设备上是一个方框。全量重生成约 30 秒。

⚠️ **标签被静默截断**：`LV_LABEL_LONG_DOT` 放不下会打省略号，**不会**报 `text overflow`。
判断办法只有肉眼看渲染图（或临时量 `lv_text_get_size`）。这就是上面几条文案为什么"短而怪"。

## 十一、第 4 套配色 `macos`（照 macOS 26/27 Tahoe 设计语言）

| 用途 | macOS 值 | 本工程取值 |
|---|---|---|
| 内容底 / 页面底 | `#1E1E1E` / `#282828` | `bg_S1=#161617`、`S1=#1E1E1E` |
| 分隔线 | `#3D3D3D`（白 25%） | `line=#3D3D3D` |
| 正文 / 次要 / 三级 | 白 85% / 55% / 25% → `#DEDEDE` / `#9E9E9E` / `#5D5D5D` | `t1/t2/t3` 依次，`t4` 取 `#7E7E82` |

**取舍（必须记下来，否则下次又会想加）**：
- Apple 的 tertiary 文字只有 **2.5:1** —— 本工程小字下限 4.5:1，所以 `t4` **不取 tertiary**。
- `KK_BLUE` 兼着左上角 App 图标块底色：官方 `#0091FF` 压白字只有 3.23:1、压 `#DEDEDE` 正文色
  只有 2.40:1，被对比度审计直接拦下 ⇒ 图标块用 Apple 无障碍档蓝 **`#0066CC`**（压白 5.57:1）。

## 十二、审计自身的教训（这一节是给未来的自己写的）

1. **审计前必须跑完布局**：LVGL 的 coords 是布局结果，建树那一刻卡片还是 `0x0`。
   `snapshot()` 里少了 `lv_obj_update_layout()`，`audit_bounds` 会把
   "还没算布局"的父对象 `[0,0]-[-1,-1]` 当成父 —— 曾因此以为系统页摘要条有 280 高（实际 44）。
2. **"卡片互相压住"这条检查默认关掉**（`PREVIEW_CARD_OVERLAP=1` 才开）。
   页面挂在 `content` 容器下（`s_ui.page[]` 不是 screen 的直接子对象），拉平卡表时
   很容易把不同页的卡混在一起比，报出跨页假重叠；而"内容被压住"本来就有更强的判据：
   `audit_text_overlap` 比的是**字形盒**，文字被压住一定报得出来。
   **一条会把好人误伤的检查，比没有这条检查更糟 —— 它逼着人改坏版面去迁就它。**
3. **报错信息本身是产物**：`audit_bounds` 只报两串坐标时，人得花二十分钟猜"这是哪张卡"。
   现在它会把 `parent=` / `child=` 的类型与文本、以及附近构件（`dump_near`）一起打出来。
   `mk_card()` 还把创建者函数名挂在对象上（`lv_obj_set_user_data(c, __builtin_FUNCTION())`），
   于是能打印 `card_tag`。
4. **绝不变量化判据**：用精确色值（卡面 `rgb(24,32,32)`）或用 `PREVIEW_CARDMAP` 的 coords。
   "亮度 22–44 当卡面"会让页底色（19,20,22）与卡面亮部（40+）混在一起，
   产出看似严谨的假结论（曾据此误判"卡片上移 76px"）。

## 十三、温度页（2026-10-06）：把"每一路能读到的温度"摊开

### 为什么加这一页

用户报障原话："最高 75 度的数据是哪里来的，不应该出现这个数据才对"。溯源结论：那 75°C
是**网卡 PHY 的结温**（NAS 上 netdata 的图名就是
`sensors.temperature_enp1s0-pci-0100_temp1_PHY_Temperature_input`），而界面上只有一块
"最高温度"KPI —— 一个孤零零的数字很容易被读成整机温度。用户随后给出方向：
"每一个能读到温度的传感器都显示出来，并自适应标记是什么设备……还需要显示设备名称"，
并明确要求"需要自适应，不要写死"。

### 采集端：自适应枚举，不再有名字表

- 旧的 `TEMP_LABEL = {"coretemp":"CPU","enp1s0":"NIC",...}` 是**按机器写死的对照表**，
  而且每台设备只取 `temp1_input` —— 这台 NAS 实际有 24 路（CPU 7 + 网卡 PHY/MAC 2 +
  iGPU 1 + 4×NVMe 14），被压成了 7 路。
- 现在 `_temps()` 遍历 `/sys/class/hwmon/*/temp*_input` 的**每一个可读通道**，设备名按
  **系统事实**推导：`/sys/class/{block,net,drm}` 里谁的 `device` realpath 和这个 hwmon
  指向同一个底层设备，就用它的名字（`nvme0n1` / `enp1s0` / 驱动名 `i915`）。
  两个必须处理的地方：① NVMe 的 hwmon 挂在 PCI 控制器上，而 block 设备的 device 在
  **下面一层**（`…/0000:03:00.0/nvme/nvme0`），所以匹配要认前缀包含；② 分区
  （带 `partition` 文件的 `nvme0n1p1`）不是独立设备，必须跳过。
- 通道名取 `tempN_label`（去掉尾部 " Temperature"），没有标签就用 `tempN`；CPU 靠
  **标签语义**（`Package` / `Core N` / `Tctl` / `Tdie`）识别，仍然不是名字表。
- 输出 `{"n","c","dev","ch"}`：`n` 是拼好的兼容字段（老固件只认它），`dev`/`ch` 给新界面。
  `TEMP_MAX=48`、`DEFAULT_LIMITS["temps"]=48`，与板端 `FNOS_MAX_TEMPS` 对齐。

### 设备名（`dn`）：不要缩写，也不要内核 id

用户看到面板后的第二句反馈是："能显示温度的设备名吗？而不是缩写。像 NIC 单独显示一个
缩写，我根本不知道它是什么设备，也无法对它进行降温。" —— 这句话把这一页的目标说清楚了：
**名字要能支持一个动作（给谁加风扇/换散热）**，所以 `enp1s0` 这种内核 id 也不合格。

采集端因此给每一路多带一个 `dn`，全部从**系统事实**里取，取不到就退回更朴素的那个：

| 设备类别 | `dn` 的来源 | 例 |
|---|---|---|
| 磁盘（block） | `/sys/class/block/<dev>/device/model` | `Samsung SSD 990 PRO 2TB` |
| 网卡（net） | PCI `vendor`/`device` → `pci.ids` 的厂商+型号（没有 pci.ids 就用厂商表 + 驱动名）+ `/sys/class/net/<if>/speed` | `Marvell AQC113 10GbE` |
| 显卡（drm） | 同上，取"厂商 + 型号/驱动" | `Intel UHD Graphics` |
| CPU | `/proc/cpuinfo` 的 `model name`（去掉 `(R)`、`CPU @ x.xxGHz`） | `Intel N100` |
| 认不出的平台传感器 | 退回 hwmon 名 | `acpitz` |

**不猜型号**：`pci.ids` 查不到、厂商表也没有时，写 `PCI 1d6a` 这样的原始号，或者干脆退回
驱动名 + 速率（`atlantic 10GbE`）。认错设备比不认识更糟 —— 用户会照着它去拆机箱。

板端为此把温度行改成**两行**（行高仍是 44），并按数据形态自适应：

```
① 有通道名（新采集端）—— 设备名独占第一行，通道名 + 数值在第二行：
Marvell AQC113 10GbE          ← 第一行：设备名（cjk_16，占满列宽）
PHY                    74.2°C ← 第二行：通道名（cjk_12，左）+ 数值（cjk_16，右，阈值色）

② 没有通道名（老采集端只发 n）—— 收成一行，数值紧挨名字，不留半行空白：
NIC                    76.0°C
```

- 一行里塞"设备名 + 通道名 + 数值"必然被截断（`Samsung SSD 990 PRO 2TB · Composite` 要
  33 个字符），两行是这个信息量的最小代价；同时**去掉了进度条** —— 44px 里再塞一条 4px
  的条，两行字就被挤成碎字，而数值本身已经带阈值色。
- **设备名必须占满列宽**：试过"名字 + 数值同一行"，结果 `Samsung SSD 990 PRO …`、
  `KIOXIA EXCERIA PLUS …` 全被截断 —— 而这页唯一要回答的就是"是谁在热"，名字被截等于没写。
- **数值不能单独占一行**：老采集端没有 `ch`，若固定两行制，屏幕上就是"名字孤零零一行、
  数值飘在右下角"（用户原话"温度界面排版完全错乱了"）。所以行数由**数据形态**决定
  （`ch` 有没有），不是由状态决定 —— 同一屏里所有行形态一致，不会参差。
- **数据可信度与阈值色分开**：`!online`（保留旧数据）时数值统一降为 `KK_T3` 灰，
  不再用危险色喊"75°C"；页头那行"保留旧数据 · 年龄"说明原因。按版面合同，
  `KK_T4` 不得用于 <20px 的文字，所以降级色用 `T3`。
- 系统页那张 300px 宽的摘要卡放不下两行，那里改成 `通道名 · 设备名`（**通道名在前**）：
  截断时先丢设备名的尾巴。NIC 的 PHY 与 MAC 的设备名完全一样，丢通道名就分不清是哪一路。
- 摘要行（全宽 900px）用完整的 `dn`：`24 路传感器 · 最热 Marvell AQC113 10GbE · PHY 74.2°C`。
- 对象顺序 = 稳定的"设备名 → 通道名"字典序，恰好落在物理拓扑上：
  `CPU`（大写在前）→ `enp1s0`(网卡) → `i915`(核显) → `nvme0n1…`(存储) → 认不出的平台热区。
  顺序不随温度变（用户明确要求"不要切换显示"）。

### 这一轮踩到的坑（写下来省得再踩）

1. **同一份几何有两处落点**：`build_rail()` 里建、`theme_apply()` 里又按旧坐标复位。
   只改一处，开机后标签被放回 43，直接越出 60 高的按钮 —— 预览的越界审计报
   `child out of parent: "总览" child=[9,116]-[66,141] parent=[8,72]-[67,131]`。
2. **行池摊派要写上限**：漏掉 `r >= per` 时，第 0 列会一路排到池底，把第 1 列的第一个
   通道重复显示一遍（预览截图里一眼可见，但几何审计不会报，因为格子没越界）。
3. **新增中文必须重建字库**：本次缺 `危/意/感/热/通/道/险` 七个字形，
   `missing glyph U+611F in 温度传感器 · 全部通道` 是预览的字形审计拦下的。
4. **度量表字段要成对**：`kk_metrics.h` 里加了 `trow_*` 字段却没人赋值时不会报错，
   只会让所有温度行叠在 y=0（`KKM` 是全局零初始化）。加字段的同一次提交里补赋值。
