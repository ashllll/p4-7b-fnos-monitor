# 面板方向、原生 FULL 与静态卡片背景：FPS 候选调查

日期：2026-10-23。范围：ESP32-P4 7B、1024×600、IDF 5.5.3、LVGL 9.5.0、adapter 0.6.4。**以下前四节是候选源码调查；当前测试状态见末节。拖动丝滑目标尚未通过，不能由候选构建成功宣布 FPS 提升。** 既有失败路线及实际在线基线见 [上游显示栈调查](ui-fps-upstream-2026-10-23.md) 和 [本轮待办验证](ui-todo-validation-2026-10-23.md)。

后续已采用原生裁剪揭示，典型帧距推进到约 16.56 ms，尾帧仍开放，见[2026-10-24 最终对照](ui-drag-lvgl96-2026-10-24.md)。本文的“当前”均指原 IDF 5.5.3／LVGL 9.5 阶段。

## 1. 面板扫描镜像替代逐帧 180° 旋转

安装的 EK79007 2.0.2~1 驱动在 `esp_lcd_ek79007.c:26–28` 定义 SHLR 为 bit 0、UPDN 为 bit 1，默认 MADCTL 为 `0x01`；`panel_ek79007_mirror():234` 通过现成 panel IO 写寄存器。`mirror(false, true)` 将这两个位设为 `0x02`，相对默认状态同时反转两个扫描方向。**它能否等价替代当前安装朝向的 180° 画面，要看实屏与触摸，不能只凭位运算判定。** [驱动固定来源](https://github.com/espressif/esp-iot-solution/blob/12f6ca1182ec48889b17ec570fadaaf267cb336e/components/display/lcd/esp_lcd_ek79007/esp_lcd_ek79007.c)

adapter 的 `lvgl_bridge_v9.c:1409` 按 rotation 分支：180° PARTIAL 调用 `display_bridge_v9_flush_partial_rotate():2720`，每片先 rotate/copy；rotation 0 调用 `display_bridge_v9_flush_triple_diff():2462`，使用原生 DMA2D copy（窗口不兼容才 CPU copy）。两者都保留三缓冲提交与最后一片的同步。因此镜像不是关闭撕裂保护，也不是启用新的 PPA renderer。[adapter 0.6.4 固定来源](https://github.com/espressif/esp-iot-solution/blob/5d75f3f0dc499d9ed4b69284a3741187c2b75a70/components/display/tools/esp_lvgl_adapter/src/display/bridge/v9/lvgl_bridge_v9.c)

最小 A/B：A 为当前正常 180° / TRIPLE_PARTIAL / 120 行；B 仅改变方向实现为 panel mirror + adapter rotation 0，并配置与实际画面匹配的触摸映射。保持两个 SW worker、UI、曲线、在线数据、手势及统计口径一致。先验证页面方向、四角／中心触摸、滚动和重复切页，再测拖动。

可证伪预测：B 不再调用软件栈的 rotate-copy 路径，flush 阶段可能缩短；若渲染仍占主导、或 DMA2D copy／帧同步开销抵消收益，整体帧间隔可能不降。无旋转 PARTIAL **仍有复制**：`prepare_partial_back_buffer():3088` 已按 dirty-buffer revision 计算 repair，必要时回退完整 baseline；`copy_diff_repair_from_front_to_back():3009` 已使用 DMA2D。未发现应再手写一套 dirty-copy 算法的依据。先前按矩形替换整帧 cache 维护曾回归，本轮不重做该路线。

## 2. 面板方向验证后，单独比较 TRIPLE_FULL

官方 adapter 明确支持 MIPI DSI 的 TRIPLE_FULL，并映射为 LVGL FULL。当前 `display_manager_use_panel_buffers():1233` 在 rotation 0 时直接复用已有面板 framebuffer 1、2 作为两块 LVGL draw buffer；不再另分配 120 行内部 RAM 绘制缓冲。rotation 非零时则走另一条旋转路径，不能混为同一对照。[官方模式与缓冲合同](https://components.espressif.com/components/espressif/esp_lvgl_adapter/versions/0.6.4/readme)

单变量门：只有镜像 + rotation 0 已通过方向／触摸检查，才将它作为 A；B 保持相同方向方案、SDK、adapter、worker 和 UI，仅把 TRIPLE_PARTIAL 改为 TRIPLE_FULL。`flush_triple_full():2400` 直接提交 LVGL 画完的面板 buffer 并轮换，省去逐片 partial copy 和 dirty repair。`buffer_height` 在该模式不代表另外申请全高内部 RAM；这与已失败的“PARTIAL 120→600 行”不是同一路径。

可证伪预测：大面积拖动可能受益于更少复制、切片与 fence；代价是 LVGL 直接在 PSRAM 画整屏，稳态小更新也会整屏重绘。旧 IDF 使用 `on_refresh_done` 兼容回调（注册处 `lvgl_bridge_v9.c:2110`），FULL 的 pending-buffer 释放仍需启动实测，不能把初始化成功当作连续呈现成功。此前只构建的 FULL 产物绑定其他 SDK／旋转组合，不应直接当作这个 B。

## 3. 竖渐变的诊断与保持视觉的缓存接缝

项目 `ui_kit/uk.c:247` 的共享 `uk_card()` 为每张卡设置竖渐变。LVGL `lv_draw_sw_fill()` 对渐变中心逐扫描行 blend；纯色中心只作一次矩形 blend，圆角仍正常绘制。`lv_draw_sw_grad_get():145` 每次申请并计算色表，`cleanup():218` 释放；当前未见持久渐变缓存开关。开启 complex gradients 也不会把现有竖渐变变成缓存。[LVGL 9.5 fill](https://github.com/lvgl/lvgl/blob/v9.5.0/src/draw/sw/lv_draw_sw_fill.c)、[gradient](https://github.com/lvgl/lvgl/blob/v9.5.0/src/draw/sw/lv_draw_sw_grad.c)

最小诊断 A/B：只把共享 card 的 `bg_grad_dir` 从 VER 改为 NONE，保留圆角、边框、数据、布局与显示链路。预测是背景 blend 调用数和 render 时间下降，而 flush 路径不变。**纯色仅用于归因，不能未经视觉确认就作为最终设计交付。** 若收益不明显，不继续扩大背景缓存实现。

若诊断有收益，候选是用原生 Canvas 只预烘静态背景，所有文字、图表、清单及输入控件保持原生可见，不采用失败的整页截图替身：

1. 实际布局完成后，以宽／高、radius、背景颜色、渐变 stops 与 opacity 为 key；用 `lv_draw_buf_create()` 分配 ARGB8888 buffer，清为透明。`lv_canvas_set_draw_buf()` + `init_layer()` + 原生 `lv_draw_rect()` 生成带 AA 圆角的背景；关闭这份 descriptor 的边框、阴影、outline 和背景图片，并清除其 `base.obj`，避免离屏生成再次触发 card 的缓存替换事件。`finish_layer()` 同步完成后才能发布缓存。[Canvas 实现及等待合同](https://github.com/lvgl/lvgl/blob/v9.5.0/src/widgets/canvas/lv_canvas.c)
2. 设置 card 的 `bg_image_src`，不缩放／平铺／recolor。**直接这样做仍保留逐行混合**：`lv_draw_rect.c:303` 自动令图片 `clip_radius=card radius`，`lv_draw_sw_img.c:314` 的 `radius_only()` 又逐行 mask + blend。[背景绘制顺序](https://github.com/lvgl/lvgl/blob/v9.5.0/src/draw/lv_draw_rect.c)、[图片路径](https://github.com/lvgl/lvgl/blob/v9.5.0/src/draw/sw/lv_draw_sw_img.c)
3. 使用正式 `LV_OBJ_FLAG_SEND_DRAW_TASK_EVENTS` / `LV_EVENT_DRAW_TASK_ADDED`：仅当该 card 缓存有效，对它的 MAIN / FILL descriptor 置 `opa=0`；对同 card 且 `src==cache_buffer` 的 IMAGE descriptor 置 `clip_radius=0`，避免再次裁剪已烘好的 AA 圆角。保留 card 原始 bg_opa、gradient、radius 与原生 BORDER，图片仍位于背景之后、边框之前。事件只改 descriptor，不在绘制过程中改对象 style 或分配缓存。[正式事件接缝](https://lvgl.io/docs/open/9.5/main-modules/draw/draw_layers.html)、[dispatch 前发送事件的源码](https://github.com/lvgl/lvgl/blob/v9.5.0/src/draw/lv_draw.c)

这能避免渐变计算与背景逐行调用，但仍使用 LVGL 的图像转换／混合。它增加一项 image task 和 ARGB8888 读取成本；不能预先保证净收益。透明边缘、RGB565 转换及边框覆盖必须与原始画面比较，不能只看节点检查通过。

## 4. 缓存生命周期与最小验收

- 卡片尺寸／背景配方变化时立即失效并断开 `bg_image_src`，回到原生渐变；在布局结束后的非绘制、非首触路径重建。translate 和数值刷新不使背景失效，除非它们改变实际尺寸。不要在 draw 回调或首触里调用同步 Canvas finish。
- 用 Kconfig 字节预算限制实际 stride×height 占用，零预算可关闭；相同尺寸／配方可共享只读 buffer，不按硬件清单数量设上限。预算不足或分配失败时继续原生绘制，记录原因；同一失败 key 不每帧重试。保留 card user_data 中既有的 body 指针。
- Canvas 删除不负责销毁外部 draw buffer。替换／删卡时由 LVGL 线程先断开引用、drop 对应图片缓存，并在无在途绘制引用时调用 `lv_draw_buf_destroy()`；共享 buffer 最后一个引用释放后才销毁。不能留下指向已释放内存的 style。
- 主机需比较 AA 四角、渐变与边框像素，覆盖主题／尺寸变化、首次入页、反向、动态清单／滚动和受控分配失败。保留现有可见节点及首次入页门禁，不隐藏原数据子树。
- 真机对每个候选单独固定源码／配置及产物，使用相同在线场景，报告首响应、render／flush 分段、帧间隔 P50/P95、窗口平均和手势漏计。稳态、动态、实际呈现与面板 60 Hz 分开记录；收益候选通过后再组合，不用一次多因素实验归因。

## 实测记录入口

### 方向候选：未通过，不保留

panel mirror API 返回成功、取消逐帧旋转后，实屏方向相对原基线反转了 180°；当前安装方向与触摸合同没有通过，源码已恢复。尝试运行中依次切换四种 mirror 组合的诊断，在等待窗口内没有输出任何 phase 标记，未取得四组对照，原因尚未确认。没有据此认定驱动或面板通用行为，也没有进入依赖正确方向的 TRIPLE_FULL 实测。

### 早期绘制对照：配置不一致，排除性能结论

镜像、纯色、内部任务栈候选的源码 sdkconfig 均显示长测关闭，但 ELF 仍含 `diag_timer_cb`，运行日志也存在诊断心跳和自动轮播。恢复文件时保留的旧时间戳使生成配置／对象没有完整重生。另一个内部栈候选还带有已撤回的镜像与 phase 标记，已单独作废。

这些试验与正常固件不能组成有效单变量 A/B。原始数据保留在本地，**不把帧间隔差异算作优化收益，也不据此断定背景缓存或内部任务栈无效**。源码已恢复原渐变、原面板方向及 PSRAM 任务栈；未提交诊断候选。后续以实际生成配置、ELF 符号、BIN 与上板身份同时核对为准。

### RGB565 混合热函数的定点 IRAM 候选

复用 ESP-IDF 正式 linker fragment，将 `lv_draw_sw_blend`、`lv_draw_sw_blend_color_to_rgb565`、`lv_color_16_16_mix` 三个现有 LVGL 函数映射为 `noflash`。本次 ELF 中三者位于 `.iram0.text`，共 2010 B。保持原 120 行 TRIPLE_PARTIAL、180°、两个软件工作线程、渐变与 PSRAM 栈；没有重写混合内核或修改依赖源码。与此前大范围 IRAM 加 64 行缓冲的失败试验分开归因。[ESP-IDF 5.5.3 官方符号放置](https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32p4/api-guides/linker-script-generation.html)

### 原生快照的遮挡剔除诊断：尚非交付实现

复查旧补丁发现，其 cover 使用 100% 百分比尺寸，实际按 viewport 的 content box 计算，受四边 padding 影响，不能盖满被失效的 viewport。主机几何断言已复现失败；按实际视口尺寸与 padding 定位后通过。该缺口可以导致原树与缓存图同时重画，旧日志没有 draw 细项计数，不能声称它解释旧试验的全部耗时。

诊断仅使用既有 LVGL Snapshot／RGB565 Image 和原生 cover check，保留原对象树可见标志及命中目标；加入 native DRAW_MAIN 计数验证剔除。局部绘制主机回归中，首次 API 入页 71 帧与指针 151 帧通过，所有已记录运动的原页面重绘计数为 0。实际 Michka 主题的局部绘制、反向和重复目标 176 帧也通过。硬件使用相同 120 行路径，正常 HTTPS 来源五组场景各两次，12 次脚本拖动无漏计，采集 570 次成功、0 次失败，无崩溃或缓冲回退。25 次已记录运动的原页面重绘均为 0，确认本候选的遮挡剔除生效。

| --- | --- | --- | --- |
| 首页 | 24.568 / 34.869 ms | 40.7 | 13.984 ms |
| 网络 | 25.239 / 34.559 ms | 39.6 | 14.026 ms |

当前原型仍在手势准备阶段同步生成两张快照，首次响应阻塞已经实测确认；内存预算、缓存新鲜度与预备生命周期也尚未完成。它不进入本轮稳定源码提交，不能由主机剔除成功宣称设备达到 60 FPS。

### 串口分片命令的实际缺陷

串口返回 `bench: 认不出 sw`，检查发现 `fgets()` 读取到未换行的短片段时，原循环立即执行 `handle()`。以真实 `cli_task()` 的主机夹具分两段发送 `bench sw`／`ipe 0 450 2\n`，中间模拟临时 EOF，旧代码明确失败于“半条 bench 不得进入解析”的断言。修复后累计到换行才解析；跨 EOF 的超长行继续丢弃整条尾巴，随后合法命令可恢复，凭据缓冲仍清零。

ASan／UBSan 及既有 token／数值／隐私回归通过，独立审查复现同一红→绿。设备实测将 `page `／`0\n`、`bench sw`／`ipe 0 450 1\n` 分别间隔 600 ms 发送：无换行时均未提前执行，完整 bench 一轮成功、零漏计。该缺陷修复保留；它解决串口验收可靠性，不能宣称提升了 UI FPS。
