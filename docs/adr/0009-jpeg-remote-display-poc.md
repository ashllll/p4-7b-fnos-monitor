# 用 JPEG 全帧与浏览器触摸注入验证远程显示

为验证[ADR-0008](0008-michka-remote-display-direction.md)，首版候选是专用Chromium渲染1024×600、CDP抓取JPEG、网关通过受保护的二进制WebSocket传输，P4硬件解码到RGB565；反向回传完整触摸生命周期并注入浏览器。

## 为什么选这条验证路径

全帧JPEG易于检查，P4具备硬件解码接口，也不要求新增网页引擎。全帧RGB565在30fps下仅图像就约295Mbit/s，不作为无线起点。H.264编码器不能被当作解码器；首版不引入软件视频解码、通用远程桌面或复杂差分协议。

代价是压缩影响细字、全帧有带宽成本、CDP实验性接口可能成为瓶颈。官方JPEG吞吐不是实际显示链路的保证。[平台依据](../michka/SOURCES.md)

## 必须保持的不变量

- 最新帧优先、固定缓冲、明确背压；不靠无限队列换取表面“不丢帧”。
- 网络／解码与LVGL显示所有权明确，DMA读取中的缓冲不复用。
- 图像与触摸统一坐标空间，事件含会话与顺序，断线清除按压。
- 画面健康与遥测来源健康分开，单纯socket在线不等于实时。
- 首版使用现有显示路径；只有测量证明必要才评估直接面板提交。

## 接受或否决条件

通过[验收矩阵](../michka/ACCEPTANCE.md)的PoC门槛后，附报告将状态改为accepted；失败则记录瓶颈，修改方案或标为rejected。不得仅因原版网页可在电脑打开就接受该技术决定。
