## 已确认问题

### 1. P1：从诊断选择当前系统页会留下空白正文

位置：`components/fnos_monitor/fnos_ui.c:3515`、`:510`。

触发：系统 → 采集诊断 → 点击侧栏系统。导航函数隐藏诊断并清掉状态，随后因为页码相同直接返回，没有恢复 `p3_note/p3_cols`。定时刷新后仍空白。现有测试覆盖诊断按钮切回、配对切回，但没有覆盖这一导航路径。

整改：统一入口状态与覆盖层可见性，在相同页码返回前完成正文同步。验收应包含所有覆盖层从当前导航项退出，并连续重复点击。

### 2. P1：底栏承诺显示最严重告警，实际上只取第一条

位置：`fnos_ui.c:2814`。

在线 fixture 的总览已显示“存在严重告警”，底栏却是黄色普通警告；系统页能看到另一条红色严重告警。代码固定读取 `alerts[0]`，不选择最高级别。采集端排列也不是全局按严重程度排序，不能靠消息先后保障正确。

整改：按严重度、时间或稳定标识选择首要事件，展示剩余条数；不能把数组首项当最高严重度。

### 3. P1：离线后旧容器状态仍显示绿色“运行中”

位置：`fnos_ui.c:3111`；离线时底栏分支仍优先使用已有告警（`:2813`）。

离线系统页虽然在摘要写了旧数据，容器行仍是鲜绿色“运行中”，旧告警仍按当前告警显示。用户扫视单行时无法区分当前事实与历史快照；温度已做灰色降级，容器缺少同等处理。

整改：统一 freshness 状态；容器显示“上次运行中”或旧快照标记，降级颜色；已有事件标记“上次采集”，离线提示优先于未经更新的健康结论。

### 4. P2：风险阈值多套且固定，界面风险与采集告警不一致

位置：`ui_kit/uk_theme.h:61`、`fnos_ui.c:3248`、`nas/fnos-agent.py:658`。

界面将所有设备 ≥60°C 判注意、≥75°C 判危险；当前采集端告警逻辑只对 CPU ≥80°C 发温度警告，没有同样的网卡/磁盘逐路规则。因而旧协议预览可以同时出现 NIC 76°C 红色“危险”和与温度无关的底栏状态。存储配色的 60/85 与采集告警的 80/90 也不同，颜色含义未解释。温度统计又把数值直接写在 UI 函数中，与主题参数形成两个维护点。

整改：定义“视觉关注区间”与“采集告警”的明确语义；按设备类别和配置提供阈值及来源，摘要、行、总览使用同一份风险模型。不要直接把所有传感器用同一固定阈值判断危险。

### 5. P2：系统三列没有窄屏重排，800×480 发生内容越界

位置：`fnos_ui.c:1166`（系统页三张等宽卡）、`:3134`（温度行内容）。

池内部能增减列，但外层始终并排三张卡。在 800×480 在线系统预览，约 181px 宽条目装入约 203px 宽内容，边界审计中止。当前 1024×600、1280×800 检查完成，不能据此声称已满足普遍自适应。

整改：按实际最小内容宽度调整外层布局，窄屏改为上下分区/分页；主内容整体允许合理滚动，并用实际长设备名验证。

### 6. P2：同型号设备的消歧标识被截断

位置：`fnos_ui.c:3142`。

系统页把设备标识放在“最热通道 · 路数”末尾。实际渲染中两台同型号 SSD 的副行都被截成 `nvme…`，无法分辨哪台设备对应温度。完整温度页保留了标识，系统摘要页仍丢失关键身份。

整改：把短设备标识置于副行开头，给状态说明降优先级；身份字段单独分配最小宽度，截断型号时保留唯一标识。

### 7. P2：失败界面引导与实际失败原因不匹配

位置：`fnos_ui.c:2272`（配对失败）、`:1831`（Wi-Fi 结果操作）。

配对写入 NVS 失败预览已经显示准确原因，但上方仍建议检查 NAS 应用和过期配对码，主体仍要求重新输入配对码。Wi-Fi 认证失败时主操作仍为“完成”，与“没连上”相冲突；同时提供的“换一个网络”不适合只需纠正当前网络密码的情况。

整改：按失败类别显示可执行的恢复动作；本地保存失败提示本地存储/重启检查，认证失败提供“修改密码/重试”，成功后才以“完成”为主要操作。

### 8. P2：总览空间分配与主要任务不符

位置：`fnos_ui.c:996`；证据 `02-live-p0.png`。

1024×600 总览的趋势卡约 140px 高，下面约 160px 区域空着，而右侧容量卡一直延伸到底部。44px 容量数字比 16px 健康结论更醒目。用户主要任务是判断设备是否正常和查看变化，当前视觉中心却偏向一个容量总数；空白来自布局高度分配，不是没有数据。

整改：让趋势卡按可用空间扩展，或有意拆成趋势与风险详情；健康结论和异常设备身份拥有更高层级。数据较少时保留紧凑的自然间距，避免把设备条目均匀拉散。

### 9. P1：温度通道收起后仍占展开高度，并伴随自动重排风险

用户补充：CPU 下方有巨大空缺，温度界面会跳切显示所有通道。本轮再查看实机温度页，确认 CPU 下方空缺和独立列滚动条；单张相机画面不能单独证明跳切过程。

新增动态主机复现：先让 CPU 通道明显分化而展开，再恢复温差很小的健康数据。CPU 块只显示设备最热温度与范围，实际高度及 min_height 却仍为 **237px**，重现空缺与不必要的列滚动。

根因位于 `ui_kit/uk.c` 的 `uk_pool_relayout` / `pool_reset`：把测得高度写入 min_height 后，下次测量只清增长态，没有清除上次最小高度。收起通道后，旧高度仍约束设备块，无法回到自然高度。

此外，`fnos_ui.c` 的温度刷新每拍根据温差、最热值与空间预算重新竞争展开资格；温度波动可改变哪个设备展开。布局签名只使用设备数与全部可见通道行数之和，无法区分“A 收起、B 展开，但总行数相同”，存在局部内容改变却未重新平衡列高的路径。空缺已动态复现；实际设备跳切的完整时间序列尚未记录，不能断言所有跳切都由同一机制导致。

整改：测量自然高度前清除旧 min_height；内容收起后重新测量并回收占位。设备位置和阅读顺序保持稳定，普通数据刷新只更新数值，展开决策采用稳定状态与明确操作，不用自动铺满空间。布局签名记录各设备身份、逐项展开状态和高度变化；通道集合或显示尺寸改变时再重排。验收增加“展开→收起→再次展开”、等总行数的设备交换展开、连续温差波动以及实机连续观察。

## 建议的整改顺序与保留项

先修温度收起占位与重排、诊断退出、告警排序和离线可信度，再统一阈值与恢复动作，最后调整空间分配和窄屏布局。均以配置、实际内容宽度和数据状态驱动，不增加固定坐标补丁。

建议保留当前五页分工、原生 Flex/行池、明确设备名称及温度单位、配对指纹分行、等待/空态和趋势断流说明。自动合并温差相近的通道已有用户指示，不应在审核中视为“少显示传感器”的回归；建议后续增加按设备展开详情入口，并相应调整“全部通道”标题。
