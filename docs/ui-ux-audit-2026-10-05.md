# fnOS 监控屏与屏幕伴侣 UI/UX 评审

评审日期：2026-10-05。对象：开发目录 `/Users/llll/code/esp/p4-7b-fnos-monitor` 的当前实现，而非资料仓中的官方示例。范围包含开发板监控、配对、诊断、插件管理页、安装/配置/卸载向导及旧采集器页面。本轮是评审，没有修改产品实现、烧录或变更 NAS 服务。

## 结论

四页导航、数字主次层级、存储滚动区、网络上下行配色已经形成可复用的基础。下一轮应优先解决 **数据是否可信、异常是否能被看到、首次连接能否完成、设置是否可靠保存**，再重排各页。继续增加渐变、分隔线或放大所有字体，无法解决这些问题。

待整改项分为 **5 项 P1、12 项 P2、2 项 P3**。另有两项配对几何问题在评审期间由并行工作修正，已从待整改清单移出。P1 表示影响核心操作或可能误导状态判断；P2 表示重要布局、反馈和一致性问题；P3 表示视觉与维护改进。这是项目优先级，不是第三方认证结果。

## P1：先修复核心体验

### UX-01：插件自动刷新覆盖未保存的设置

**已复现。** `index.html:306–311` 每两秒重填表单。数字输入框只在保持焦点时受保护；下拉框没有保护。浏览器中端口从 `8798` 改成 `8808`，点击另一字段后，下一轮刷新恢复 `8798`。用户可能以为保存了自己的改动，实际提交的是被刷新覆盖的值。

整改：将“服务器状态”和“编辑草稿”分开。进入编辑后保留全部 dirty 字段；保存成功才更新基准，失败保留草稿；提供“放弃修改”，离开时提示未保存内容。两个保存请求的部分成功也要明确说明，避免 `/api/config` 成功、容器设置失败后只显示笼统错误（同文件 `408–418`）。

验收：数字和下拉字段编辑、失焦、等待至少三轮刷新均不回退；保存成功/失败/部分成功有可见反馈。

### UX-02：模块读取失败或关闭时，主指标仍像有效数据

**源码确认，匿名页面夹具可观察。** 采集器会保留旧值，并提供 `modules.status/ts/error`（`fnos_collector.py:654–663`）。开发板解析采集段状态，但只在诊断页显示，未用于 KPI 和列表的可信度；解析也没有保留模块时间（`fnos_data.c:143–169, 255–273`，`fnos_ui.c:1276` 起的 `refresh`）。因此整帧 `ready` 为真时，某段失败仍可能显示旧值或零值；主卡片看不出区别。

Web 的 `renderCards` 同样不读取模块状态（`index.html:229–262`）。例如容器采集关闭显示“0 项”；缺少运行时长显示“0 分”；数值缺失的进度条按零画。浏览器夹具中网络模块“权限不足”，网络卡却仍按正常格式展示数值。

整改：每个指标/列表就地显示 `正常 / 旧值及年龄 / 权限不足 / 未支持 / 已关闭 / 等待`。未知值使用 `—`，不绘制零值健康条；关闭容器采集不能解释成“没有容器”。总览同时报告“数据不完整”，避免只按采集告警决定绿色结论。

验收：首次读取失败、读过后失败、权限不足、关闭、无来源、未知新模块状态均有独立夹具；这些状态不得伪装成实时零值或健康结论。

### UX-03：Web 请求断开后仍保留绿色“运行中”和冻结的数据年龄

**已复现。** `refresh` 只有 `finally`，没有处理 fetch rejection（`index.html:359–370`）。中断本地夹具服务后，控制台持续 `Failed to fetch`，页面仍保持“运行中”和“1s 前”。只有收到带 `error` 的响应才改顶栏，连接失败本身不会更新可信状态。

整改：捕获网络/解析错误；独立按本地时间更新最近成功时间，进入陈旧/断连状态；保留旧值但标明快照。状态请求成功而指标请求失败也不能继续暗示指标正常。重试进度与手动重试应可见。

验收：断网、服务停止、超时、HTTP 错误、无效 JSON、单个接口失败分别显示明确状态；恢复后自动回到有效数据，年龄继续正确增长。

### UX-04：告警先截断后统计，可能漏掉严重事件

**确定性夹具复现。** 采集器按“阵列 → 卷 → CPU → 内存 → 容器”追加事件，直接返回 `out[:8]`（`fnos_collector.py:435–460`）。八条阵列同步信息加一条 99% 用量卷的严重告警，结果是总数 9、发出 8 条 info、严重事件未发出。开发板健康结论只统计收到的列表，因此可能得到绿色“无采集告警”。协议已有 `trunc` 总数/丢弃信息，但界面没有消费它（采集器 `687–691`）。

整改：在截断前按严重程度排序；独立传递完整严重/警告计数及最重要事件，列表截断不改变健康判断。明确显示“显示 8 / 9，另有 1 项”，提供插件端完整查看路径。

验收：超过上限且严重事件位于尾部时，严重告警仍出现在总览首位；总数、展示数、截断数一致。

### UX-05：通用固件缺少 NAS 地址、端口及 Wi-Fi 的首次连接入口

**源码确认；影响配套插件发行。** 开发板配对界面只有六位码，`fnos_pair_begin` 也只接收 code（`fnos_pair.c:631–643`）。实际 host/port 来自编译配置或既有 NVS，首次配对不能指定新的 NAS。模板默认 `nas.local:8799`，插件向导默认端口 `8798`；Wi-Fi 也在配置模板中填写（`fnos_config.example.h:5–16`）。六位码只能证明配对请求，不能替代服务发现或目标地址。

整改：首次使用流程为“连接网络 → 发现/输入 NAS 地址与端口 → 检查伴侣服务 → 输入配对码 → 核对证书 → 完成”。服务发现可以作为便利入口，但保留手动地址；在输入码前明确显示目标 NAS。统一配套插件的默认端口，保留开发采集器迁移路径。

验收：使用无个人配置的通用固件，在一个全新 NAS 地址上通过界面完成连接与配对，不要求用户重新编译。当前设备已联网，不等于首次使用流程完整。

## P2：信息架构、布局与反馈整改

### UX-06：总览健康条缺少“具体发生了什么”和跳转

总览提示“存在严重告警”，右侧主要是运行时长、容器数和计数；用户还要切到系统页找原因。趋势卡高 304px，但曲线只有 114px，图例以下留有约 100px 空白（`fnos_ui.c:553–581`）。

重排：顶部保留 NAS 身份、信任/采集状态；健康区直接显示最高优先级事件和“查看”；四个 KPI 保留；下方分为较紧凑的资源趋势、存储风险摘要。利用空白承载 1–2 条需处理事项，不再重复计数。无异常时才显示简洁健康摘要。

验收：从总览能在一次阅读中知道异常对象、原因和下一步，点击进入对应卷/阵列/服务，而不是仅看到“严重 1”。

### UX-07：存储汇总掩盖局部满卷，异常阵列可能藏在滚动下面

全卷加权用量正常，不代表每个卷都有空间；预览中总用量约 67%，单卷已 96%。默认仍按名称展示，阵列区域首屏约三条，后面的降级阵列需要滚动。Web 存储与阵列只展示前四项，虽然存储标题有总数，却没有“还有两卷”的入口（`index.html:245–249`）。

重排：容量总量作为背景信息；优先显示“最满卷、最低剩余空间、异常阵列及同步进度”，下面为完整卷列表与磁盘活动。状态异常置顶应保持对象身份稳定，不能每秒随数值跳序。Web 增加展开/完整列表及展示数量。

验收：第六个卷满、第六个阵列降级时，首屏仍有明确提示；完整条目可达。

### UX-08：系统页将普通容器、温度与严重事件等权排列

三列等宽，关键告警在最右；容器名称与状态上下分离，状态靠右，行间距较大；告警是英文自由文本，没有级别标签、时间或对象跳转（`fnos_ui.c:638–674, 1450–1540`）。采集器将运行容器排在停止容器之前，温度/磁盘还按实时数值排序（`fnos_collector.py:331,375,400`），读者容易在更新中失去正在看的对象。

重排：系统页上部优先展示异常/事件；下部左右排列容器与温度。容器行采用“名称 + 同行状态”，次行仅显示必要退出原因；区分正常停止与意外停止。告警结构化为级别、对象、简短中文原因，保留原始技术详情供展开。列表默认保持稳定身份顺序，严重异常可固定在单独区域。

验收：停止的重要容器不藏在一屏正常容器之后；长名称和两行告警不被裁切；刷新时正在阅读的对象不跳位。

### UX-09：网络页重复信息过多，图表难以估计时间和数值

“采集延迟/采集耗时”上下重复，“接口”也重复；顶部吞吐率自动换单位，图例峰值固定 KB/s，底部累计量固定 GB。图表只给顶部量程，没有清晰的横轴时刻与中间纵轴刻度（`fnos_ui.c:build_p2, refresh`）。极大瞬时值会让原有小流量曲线贴底，这属于自动量程的设计取舍，不将夹具的突增直接当作采集错误。

重排：上方仅保留上行、下行、明确标注的双向合计；采集链路耗时/成功率移入可折叠质量区。图表增加“窗口开始/现在”与少量纵轴刻度；当前、峰值、累计量分别使用一致格式函数。量程收缩采用滞后，突增时解释量程变化。

验收：用户能区分 NAS 网卡吞吐与开发板到 NAS 的 HTTP 耗时；相同值在 KPI、图例和摘要中的单位一致。

### UX-10：离线时局部绿色状态仍像实时状态

总览 KPI 数字变灰，但容量条、系统容器“运行中”和存储阵列“正常”仍保留健康色；网络大数字保持鲜亮（离线预览）。顶栏虽写“旧数据”，视线停在局部卡片时仍容易误读。

整改：保留最后快照，但每个区域有轻量“旧值 · 时间”标识，健康色降饱和或切为中性。趋势的最后有效采样点和断流区要明确；没有有效历史时显示“历史不可用”，不要显示“峰 0”。

验收：遮住顶栏观察单个卡片，仍能辨别它是实时值还是旧快照。

### UX-11：配对失败信息与三步指引互相覆盖

**预览确认。** `pair_steps` 在卡片 `(16,80)`；`pair_msg` 在 `(16,84)`。失败阶段同时显示它们（`fnos_ui.c:831,914,1081–1110`），导致“连不上 NAS，检查 Wi-Fi 与地址”与“三步完成配对”标题重叠。错误提示离输入框也较远；忙碌状态留下大片空模块。

整改：为输入状态、操作反馈、指导步骤分配不同区域。字段错误紧贴配对码；服务错误用独立状态条。忙碌阶段显示明确进度与可取消/可关闭的后果，不保留空白码框。解除配对用独立确认说明；超过一定时间/退出页面后解除确认应重置。

验收：空码/不足六位/错误码/过期/网络错误/证书错误分别截图；任何状态下文字和按钮不重叠。

### UX-12：插件配对页按开发调试流程组织，普通用户路径不完整

生成码后主要展示 curl、Python、证书文件命令（`index.html:138–139,382–403`），与开发板已有触屏键盘的使用方式不一致。首先显示长篇 TLS 技术说明，把主操作推到下面；`0.0.0.0:8798` 是监听配置，不能作为开发板连接地址。Web 指纹为一长行，开发板为四行，不便逐段比对。后端提供 `pairing.expires_in`，页面仍只显示静态“300 秒内有效”（服务端 `811–812`）。

重排：顶部显示可连接的 NAS 地址与“生成配对码”；其后是六位码、倒计时和开发板操作图示/文字；核对阶段两端使用同样的四组指纹；设备列表独立为管理区。curl 和引导通道细节移入“高级调试”。显示过期、已使用、已作废，并给重新生成入口。

验收：用户仅按触屏与插件页面说明完成配对，不使用终端；监听地址与连接地址不会混淆。

### UX-13：撤销设备的结果显示到隐藏的设置页

`index.html:321–324` 在设备配对页操作撤销，却把结果写入服务设置页的 `cfghint`。确认框未包含设备名称；错误响应也可能变成“未找到该设备”，因为没有展示 `r.error` 的内容。

整改：反馈放在设备列表附近，明确对象、成功/失败与下一步；操作进行中禁用该行按钮，失败保留原行。危险确认列出名称/最近访问，避免相似设备误操作。

验收：成功、设备不存在、HTTP 错误、网络失败均在当前页有可见且正确的反馈。

### UX-14：应用中心配置向导显示默认值并整体覆盖当前配置

`wizard/config:7` 已明示表单是安装默认值，`cmd/config_callback` 会整体应用并重启。文案透明，但操作模型仍不合理：仅想改一个采样间隔，容易同时把已经调整过的端口、监听与容器设置恢复默认。

整改：平台允许时由当前配置初始化；若无法动态初始化，将常规编辑统一引导到应用管理页，向导只负责明确的重置/修复流程。后端仍保留数值范围校验，前端也显示具体范围；不要让安装时“2–5 位数字”校验替代真实端口范围。

验收：修改单字段时其他生效配置不变；重启失败明确区分“配置已保存”和“服务未恢复”，可返回上一个可用配置。

### UX-15：同一指标在两端的阈值与颜色语义不一致

Web CPU/内存条从 75% 变橙（`index.html:224`），开发板从 80% 变橙；温度条 75°C 已红，但采集器 CPU 温度 80°C 才发 warn（`fnos_ui.c:1479–1480`，采集器 `449–450`）。令牌头还有不同于实际刷新逻辑的通用阈值。存在“红色指标 + 绿色无采集告警”的解释缺口。

整改：建立按指标类型的阈值合同，区分视觉注意、采集告警和硬件故障，不把 CPU/NIC/磁盘套成同一种温度标准。优先由协议提供状态与原因，两端一致渲染；如某种红色只是视觉注意，名称和健康汇总应解释。

验收：边界值前后截图两端一致；同一事件的严重程度、名称和总览结论不冲突。本轮未验证设备传感器的硬件安全阈值。

### UX-16：诊断缺少完整可查的异常列表，端点取值也可能不是真实连接目标

开发板“采集段”最多列两段，其余只有省略号；用户看得到问题数量，却没有继续查看入口。诊断端点直接显示 `FNOS_HOST/FNOS_PORT`（`fnos_ui.c:1484`），配对层实际会加载 NVS 地址，后续换固件/配置时两者可能不一致。

重排：诊断先显示当前实际连接目标、最近成功时间、明确错误及建议处理；模块异常可滚动查看全部；HTTP、堆内存、原始协议等放在次级技术详情。端点取自实际活动配置，不能取编译模板。

验收：四个模块失败时都可查；活动目标来自 NVS 时，诊断地址与实际请求一致。

### UX-17：Web 自动重建控件和状态缺少无障碍语义

每两秒重建设备表的 `innerHTML`，可能丢失键盘焦点与操作上下文（`index.html:315–324`）；页签只切 CSS class，没有表达选中关系；保存/配对提示无 `role=status` 或适当 live region。原生 input 和 label 已有关联，不能笼统认定所有表单都不可访问。

整改：稳定更新现有行，保留焦点；为页签增加选中/控制关系与键盘行为，状态消息可被辅助技术感知。采用可见 `focus-visible`；处理请求中的禁用与反馈。本轮未使用真实屏幕阅读器，也不宣称已完成 WCAG 合规审计。状态消息依据见 [W3C 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。

验收：仅用键盘完成切页、编辑、保存和设备操作；刷新后焦点不丢失；成功/错误消息能被辅助技术读取。

## P3：视觉与设计合同优化

### UX-18：Web 字号和窄窗口头部层级不佳

页面标题 15px、卡片标题 11px、状态标签 10.5px，信息较密；390px 窗口下“NAS 屏幕伴侣”被压成多行，版本/uid/seq 徽标占据头部。指纹需要横向滚动比对。没有观察到该匿名夹具的整页横向溢出，不能直接声称全部表格都会溢出。

整改：标题与主要操作提高层级，普通正文适当增大；窄窗口只保留名称和状态，版本/uid/seq 收入诊断；表格按重要字段响应布局，指纹四组换行。增加主题令牌与浅色方案或平台主题适配，是否必须跟随飞牛主题应另行核对官方要求，本轮不把它视为上架硬性条件。

### UX-19：设计说明、实现和产品文案需要统一

当前 UI 有 v6/v7/v8 多份说明，令牌头、设计说明与实际实现的表面样式存在漂移；评审快照使用渐变与描边，收尾的并行修改又去掉渐变。预览文字断言也出现漂移。能力矩阵写“P0”“包用户”“Python”，这些适合诊断人员，却占据常规使用文案；旧 agent 根页面直接显示 JSON，应该明确标为开发诊断入口。

整改：维护一份当前设计合同：页面任务、状态机、字号/间距/颜色、阈值、单位、长文本与长列表、焦点和按钮反馈。发布页面使用普通用户语言；协议、路径与开发阶段名进入高级详情。保留旧 JSON 工具用于排障，明确与正式伴侣管理页的关系。

验收：文档示例、预览断言、通用配置和产品操作说明使用同一套术语与流程。

## 推荐的页面重排

| 页面 | 首先回答的问题 | 推荐次序 |
| --- | --- | --- |
| 总览 | 这台 NAS 现在是否需要处理问题？ | 身份及数据可信度 → 最高优先级事件及跳转 → 四个 KPI → 资源趋势与存储风险 |
| 存储 | 哪个卷/阵列有风险？ | 异常卷/阵列摘要 → 全部卷 → 阵列及同步进度 → 磁盘活动；总容量退为辅助信息 |
| 网络 | 当前收发多少，最近有什么变化？ | 上下行与双向合计 → 带刻度趋势 → 累计量/接口；采集链路质量放次级区 |
| 系统 | 哪个服务或硬件需要关注？ | 异常事件 → 容器与温度；普通运行服务不压过意外停止服务 |
| 配对 | 下一步具体要做什么？ | 网络/目标 NAS → 配对码 → 指纹核对 → 完成；每阶段只有一个明确主操作 |
| 诊断 | 为什么连接或指标异常？ | 活动目标与最近成功 → 原因与建议 → 全部模块状态 → 技术详情 |
| 插件首页 | 伴侣是否就绪，开发板是否连接？ | 服务/采集/配对状态摘要 → 待处理事项 → 配对入口 → 核心指标；能力来源收进诊断 |
| 插件设置 | 哪些值正在生效，哪些尚未保存？ | 基本连接/采样 → 高级权限/传输 → 草稿操作条 → 重启待生效状态；路径进诊断 |

保持现有四个监控页的导航名称；配对与诊断属于设置/维护路径，不应让顶栏仍像在浏览“系统数据”却缺少返回位置说明。第一次使用可直接进入设置向导；完成后回总览。

## 实施顺序与验收门槛

1. **先修可信状态与操作可靠性**：UX-01～05；模块旧值/缺失、断连年龄、完整告警统计和通用首次连接是布局的基础。
2. **再重排信息**：UX-06～12；先形成总览、系统、配对的静态排版，再应用一致的单位、列表和状态组件。避免一边修数据语义一边反复重画全部页面。
3. **完善管理流程**：UX-13～17；保存/撤销/重启/倒计时/键盘焦点。配置向导与管理页要有单一明确的常规入口。
4. **收敛视觉合同**：UX-18～19；字号、主题、按压/禁用反馈与术语，并同步预览场景。

必要回归场景：首次无数据、正常、模块旧值/失败/关闭、服务断连/恢复、告警超过上限、极长名称、超长列表、窄窗口、配对错误/过期/成功/解除、夜间。检查文字边界、父子控件裁切、实际可触范围和焦点保留，不能只查“文字存在”。

最终需要一次通用配置构建、明确产物与烧录版本、串口运行证据及物理相机画面，才能验收开发板效果；插件还需要实际 fnOS 网关/安装/重启/卸载流程。主机预览与匿名浏览器夹具只能证明对应部分。
