# 触控调度优化与验证（2026-10-12）

本轮针对左右切页卡顿、滑动跟手差，先在开发工程完成实现与验证，再按明确文件清单同步到独立发布工程。任务开始时开发工程已有大量未提交修改，本轮采用修改前文件快照作为差分基线，不能将开发分支 HEAD 当成完整测试基线。

## 改动

- `fnos_ui.c`：指针读取定时器读取完成后，立即把当前指针样本交给页面手势控制器。原先读取定时器与手势定时器可能以相反顺序运行，导致新样本等到下一次 LVGL 调度，再叠加期间绘制与刷屏的耗时。
- 保留驱动读取回调、定时器 user data、显式读取的手势轮询兜底和台架注入接口。复用 `UK_GESTURE_POLL_MS`，没有加密硬件采样或修改手势阈值。
- `preview.c`：记录采样到页面跟随的间隔；对单步有效横拖要求同一次采样即出现跟随。纵向滚动回归从当前内容页寻找滚动区，避免误选底部导航并触发另一种操作。
- `stack_check.py`：把新增定时器回调纳入显式检查列表。
- `fnos_perf.c`：修复台架每轮的采样标记、拖动步数及帧边界重置；首轮点击也先落到其他页面，确保测量真实导航。
- `perf_bench.py` / `test_perf_samples.py`：采集器要求每轮均有按下与松手计时，且无漏响应，否则拒绝记录为有效结果。分片、损坏记录、缺失计时及旧 CSV 回归共 5 项通过。

## 主机验证

新增回归先在旧实现上失败（短横拖/短快划：采样 8 ms、跟随 9 ms），再在新实现上通过（采样 8 ms、跟随 8 ms）。这里的毫秒是主机预览的虚拟时间，只证明少等一次调度，不能当成实机触控延迟。

800×480、1024×600、1280×800 的运动回归通过，覆盖抖动、取消、短快划提交、原生滑动、纵向滚动隔离、快速转向。API 切页首次位移 16 ms、完成 166 ms；首次进入系统页、重复同一目标、冻结历史及末帧像素回归通过。

完整预览门禁通过：状态样张、字形、标签溢出、父子几何、点击区域重叠、格式残留、对比度、动态硬件清单与分配失败恢复。已实际查看生成样张。

ESP-IDF 5.5.3 / ESP32-P4 构建通过。静态栈检查通过：主任务下界 4592/16384 B、LVGL 任务下界 4496/12288 B、数据轮询任务下界 4544/6144 B。静态检查无法覆盖全部间接调用与中断嵌套，不代表运行栈的绝对上界。

## 实机验证方法

重建修改前基线和优化版，二者均使用修正后的相同台架，并只开启相同的 `CONFIG_FNOS_UI_MOTION_STATS` 与 `CONFIG_FNOS_UI_PERF_BENCH` 临时测量开关。除本轮触控改动外，SDK 配置一致。普通配置随后按字节恢复，保留普通基线与优化版固件供回滚。重建的基线不能保证与任务开始时设备中原有固件逐字节相同。

串口台架通过真实驱动读取路径注入手势，计时起点是 LVGL 收到样本，终点是 `LV_EVENT_RENDER_READY`；它覆盖输入后的处理与绘制，不能测出手指接触面板至光学显示的完整延迟。板屏照片只用于检查可见布局和启动状态，单张照片不能证明不卡顿。

固定顺序测量先跑滑动、真实点击、静置各 6 组，每组手势 3 轮、静置 5 秒，各先丢弃 1 组预热。首次按下响应呈快慢两档，小样本中位数不稳定，因此额外对滑动各测 20 组：每组触发前加入 0–500 ms 随机等待，种子为 `20261012`，两版复用相同参数；扩充测量顺序为优化版后基线，与首轮顺序相反。每行都要求 `cycles=p2f_n=r2f_n=3`、`misses=0`。

`p2f` 统计按下样本后的下一次渲染就绪事件，不区分该帧是否已经产生页面位移；页面跟随的同次采样性质另由主机像素/状态回归验证。本文不将它解释为完整的手指到屏幕响应。

第一次实机采集发现既有台架多轮未重置标记，`cycles=3` 却只有 `p2f_n=1`、`r2f_n=1`，且首轮点击当前页。该组结果全部标为无效并保留，不能把执行计数当成完整响应样本。最终结论只采用修正台架后的复测。

## 实机结果

下表对每组报告的 p50 / p95 列分别取中位数，**不是**把全部帧合并后计算分位数。扩充滑动为每版 20 组、60 次完整按下与松手计时，台架 `misses=0`；固定点击为每版 6 组、18 次完整计时，台架 `misses=0`。

| 指标 | 修改前基线 | 优化版 |
| --- | ---: | ---: |
| 扩充滑动：按下采样到下一帧就绪 | 73.24 ms | 71.01 ms |
| 扩充滑动：松手采样到下一帧就绪 | 34.14 ms | 16.54 ms |
| 扩充滑动：连续帧间隔 p50 | 29.05 ms | 28.26 ms |
| 扩充滑动：连续帧间隔 p95 | 36.40 ms | 34.72 ms |
| 固定点击：松手采样到下一帧就绪 | 110.98 ms | 112.48 ms |
| 固定点击：帧间隔 p95 | 128.51 ms | 132.73 ms |
| 固定静置：UI tick p50 | 36.94 ms | 36.87 ms |

稳定收益是滑动松手后的渲染响应减少约 **52%**。持续滑动帧间隔改善幅度较小，真实点击换页未显示明显收益。首次按下仍有快慢两档，约 37 ms 的 UI 周期处理开销也仍存在。

固定 6 组滑动的按下首帧统计曾为 44.6→77.0 ms，触发了额外调查；扩到 20 组并打散触发时机后为 73.2→71.0 ms。两版都出现约 15 ms 与 70–80 ms 的运行组，不能依小样本中位数宣称按下响应显著改善。该指标记录任意下一渲染帧，解释还受前述边界约束。

日常版已烧录，应用文件 SHA256 前缀为 `d414e0e427ea`，三个镜像均通过设备端校验。测量开关关闭，SDK 配置按字节恢复，工作区构建产物与实际烧录文件一致。70 秒启动日志中 ELF 指纹 `d63df2de7` 与该固件一致，六页 UI 创建完成，主任务正常返回；未发现 panic、栈保护、看门狗、断言或堆损坏记录。

已用 Android 相机查看新拍板屏：总览页恢复在线并显示 NAS 数据，照片中计数为 `ok=66 fail=0`。照片存在灰尘和拍摄角度影响，仅用于可见布局与在线状态检查；自然手势的主观跟手感仍待用户反馈。本轮为短时运行与台架验证，未进行长时间浸泡测试。

原始串口、照片、本地配置及可回滚固件均留在本机任务证据目录，不加入仓库。实测固件使用本地开发配置；公开源码另用模板配置构建验证，个人固件不随源码发布。

构建助手曾选择缺少依赖的 Python，实际构建使用经核实的工程 `idf.sh` / ESP-IDF 5.5.3 环境。烧录保存的 A/B 产物使用该环境的官方 esptool：逐个核对固件 SHA256，按保存的分区清单写入，要求三个镜像均完成设备端校验；未擦除 NVS。
